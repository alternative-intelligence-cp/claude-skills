# 0.2.3 — the worker inside: headless dispatch, identity, permissions, liveness, measured budget — PLANNED

> The spec calls this the step that matters and it is: until a real worker's
> `Write` tool call lands in `upper/` and not on the host, everything before
> it is substrate. It also fixes four things the run found that have nothing
> to do with containment — self-reported budgets, self-reported model ids,
> the verifier that could not build a mutation, and the permission grant
> that withheld commands the loop needed.

## 2. Decisions

L-2, L-4, L-6, L-7 apply. Local:

- **L-3.1 — a worker's identity inside is `DEVTEAM_PARENT_SESSION=<the
  board's writer id>`, set by the harness, and the guard treats a payload
  carrying it as the run's own agent.** *Why:* today a subagent inherits its
  parent's session id and the guard's scope rule keys on it; a headless
  process has a fresh id and would be refused its own task file (P-13).
  *Fails closed:* absent variable → `unknown`, never `theirs` — the exact
  defect that left the guard inert for a rehearsal (DESIGN §20) must not
  come back through this door. The guard's control gets both cases.
- **L-3.2 — the harness measures budget and model; the worker's own
  `budget:` and `model:` lines are cross-checked against it, not trusted.**
  *Why:* P-17c — today both are self-reported by the party least placed to
  know; the CLI's JSON result carries usage and the model actually used.
  A mismatch is a finding (`budget-mismatch`, `model-mismatch` in
  `check_report`), not a correction.
- **L-3.3 — the inside permission set is generated from the role's agent
  definition, one home, and passed with `--allowedTools`.** *Why:* a tool
  list in an agent file is the only enforced restriction the 0.1 design had
  (DESIGN §2 says so); making it the source of the headless allowlist keeps
  it enforced and keeps it single. *Declined:* a second list in
  `PERMISSIONS.md` (two homes; F-6, F-24, F-30 were all a grant and a rule
  disagreeing).
- **L-3.4 — read-only roles stay `Agent`-tool subagents and use `sandbox.py
  exec` for anything that must mutate.** *Why:* they cannot write anyway;
  the cost of headless (no `ListAgents`, no transcript) buys them nothing;
  and `exec` gives the verifier the mutable copy F-100 said it could not
  have. *Cost:* two dispatch mechanisms exist; the supervisor's skill says
  which role uses which, in one table.

## 3. The work

### 3.1 `sandbox.py dispatch <id> --role <r> --model <m> --dispatch <file>`

A `run` specialised for a worker:

- the command is `claude -p --output-format json --plugin-dir <plugin root>
  --model <m> --allowedTools <from 3.3> --no-session-persistence
  --settings <meta>/settings.json` with the dispatch file's contents as the
  prompt, prefixed by one line: *"You are a devteam `<role>`. Invoke the
  `devteam:work` skill and follow it."* — nothing else, because the skill is
  the procedure and a prompt that restates it is a second home (P-34)
- `meta/settings.json` disables the harness's own sandbox inside
  (`{"sandbox":{"enabled":false}}` — the observed key from 0.2.0 §3.3 item
  6) so `bwrap` is not nested, and carries no permission allowlist (the
  `--allowedTools` flag is the allowlist; a prompt inside a headless run is
  a denial, which is P-39's behaviour exactly)
- `--timeout` from the dispatch's estimate × 3, or the supervisor's argument
- the JSON result is written to `meta/result.json`; the `result` text — the
  REPORT block — to `meta/report.txt`; usage and model to `meta/budget.json`
  as `{tokens, minutes, model, cost_usd}` using the field names 0.2.0 recorded

### 3.2 Credentials and identity inside

From 0.2.0 §3.3's working variant. If **A** (a copy of
`~/.claude/.credentials.json` into the tmpfs `HOME/.claude/`): the harness
copies it at `dispatch` and the copy dies with the tmpfs. Record the risk
plainly in `meta/plan.json` and in 0.2.4's docs: **a token refresh inside
the sandbox is lost, and if the provider rotates the refresh token the
host's copy may be invalidated** — `REASONED`; watch for it in 0.2.9 and
record what happens. If **B** (an environment variable): add it to the
allowlist (0.2.1 §3.3) and to nothing else.

Git identity: `--clearenv` removes it and `~/.gitconfig` is not bound, so
`git commit` inside fails with "please tell me who you are". The harness
reads `git -C <repo> config user.name` and `user.email` **on the host** and
sets `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`,
`GIT_COMMITTER_EMAIL` inside. F-44 (author email differs by layer) becomes
explicit and identical by construction.

`DEVTEAM_PARENT_SESSION` (L-3.1) and `DEVTEAM_SANDBOX` (0.2.1) are set.
Nothing else from the host environment crosses.

### 3.3 The inside allowlist, generated

`sandbox.py allowlist --role <r>` prints the `--allowedTools` value derived
from `agents/<r>.md`'s `tools:` line, translated: `Bash` becomes
`Bash(*)` **minus** the outward set, which is the by-name list in
`templates/PERMISSIONS.md` §"Deliberately not requested" reduced to what
structure does not already make impossible — `Bash(git push:*)`,
`Bash(gh:*)`, `Bash(pip install:*)`, `Bash(uv add:*)`, `Bash(sudo:*)` — as
`--disallowedTools`. Everything filesystem-shaped is allowed (L-7).
`WebSearch`/`WebFetch` only for a role whose agent file lists them.

A control asserts the generated list for each of the three worker roles
against a golden file, and that changing an agent's `tools:` line changes
the output (the two-declared-lists test: agent file ↔ allowlist).

### 3.4 Dispatching from a supervisor, and the ten-minute wall

The supervisor's `Bash` call runs `sandbox.py dispatch … ` with
`run_in_background` (`../README.md` §4.5). 0.2.0 §3.4 measured whether the
backgrounded parent keeps the worker alive; build on what it observed:

- if it survives: `dispatch` writes `meta/pid`, and the supervisor is
  re-invoked by the harness when the process exits; it then reads
  `meta/report.txt`
- if it does not: `dispatch` double-forks a detached process with its own
  session (`setsid`), writes `meta/pid`, and the supervisor polls
  `sandbox.py status <id>` at an interval it states in the heartbeat; the
  `--die-with-parent` semantics then bind the worker to the detached
  reaper, whose own death kills the worker — record this in `status`'s
  output so recovery can see it

Either way the heartbeat (`devteam/.run/locks/<TASK>.heartbeat`) gains the
sandbox id: `waiting on S-n (<role>, dispatched <time>, sandbox <id>)`.

### 3.5 Liveness: the fourth signal

`devteam/.run/locks/<TASK>.sandbox` — written by `dispatch`, rewritten at
exit, never deleted (the 0.1 rule about heartbeats, same reason):

```
T-2 S-3 <id> pid <n> started <iso> step-timeout <s>
T-2 S-3 <id> exited <code> at <iso>            (rewritten at exit)
```

`run` §3's recovery table (0.2.4) reads it after `ListAgents`, the heartbeat
and the tree: a live pid under a claim whose supervisor is gone is a worker
still writing its overlay — **not** a stale claim; a dead pid with a
non-empty `upper/` is work to inspect with `close --keep`, not to discard.
After a session restart, `--die-with-parent` has already killed every
worker, so every `.sandbox` line reads `exited` or names a dead pid — that
is P-14's "every claim is stale after a restart", now with a reason a
reader can see.

### 3.6 `check_report.py`: `budget-mismatch`, `model-mismatch`

When `meta/budget.json` exists for a step (the sandbox root is findable
from the `.sandbox` file), compare the REPORT's `budget:` and `model:`
against it. Tokens within 10 % or minutes within 20 % pass — the worker
cannot see the harness's exact counter; a `model:` that names a different
id fails. Controls for both, and the false-positive twin (a worker whose
figures match).

**Do not** make the check depend on the sandbox root being present: a
report from a `guard-only` project (0.2.4 §3.6) has no `budget.json`, and
the finding must then be silent, not `could not run`.

### 3.7 The verifier's mutation, and the auditor's experiment

`verify/SKILL.md` §"Where a mutation goes" currently prescribes a scratch
directory outside the repository because the guard refused in-tree writes
by a role holding no claim (F-100). Replace the recipe with
`sandbox.py exec --repo <repo> -- <the mutation and the check>`: the whole
tree is mutable, nothing survives, and the command's exit code and output
come back. The same for `audit/SKILL.md` where it tells an auditor how to
try something. Both roles keep their agent definitions (no `Write`); `exec`
needs only `Bash(python3 …/sandbox.py exec:*)`, which 0.2.4 adds to the
grant.

## 4. Verification

The spec's S-6 expectation, measured: an implementer dispatched through the
harness on a throwaway project with a one-step dispatch (*"create
`src/hello.py` printing hello; verify with `python3 src/hello.py`"*):

```
sandbox.py dispatch <id> --role implementer --model <cheapest> --dispatch d.txt
    → exit 0; meta/report.txt holds a REPORT block; meta/budget.json holds numbers
ls <root>/<id>/upper/src/hello.py     → present
ls <repo>/src/hello.py                → No such file or directory   (host untouched)
sandbox.py promote <id> --dry-run     → no findings; one would-be commit
sandbox.py promote <id>               → promoted <old> → <new> T-1.S-1: …
python3 …/check_report.py <repo> T-1   → clean, including budget and model
```

Controls: `test_sandbox.py` gains the allowlist golden cases, the identity
cases (`DEVTEAM_PARENT_SESSION` present → the guard treats a `devteam/tasks/`
write as the run's own; absent → `unknown`, refused), and an `exec` case
that mutates a test and sees it fail. `test_guard.py` gains L-3.1's two
cases. `test_check_report.py` gains 3.6's three.

## 6. Do not

- do not pass the host's `~/.claude` or `~/.claude/settings.json` into the sandbox — the settings carry the operator's hooks and permissions, which are not the worker's
- do not let the worker inherit the supervisor's `CLAUDE_SESSION_ID` as its own `--session-id`; the parent identity is the environment variable, and the CLI's session is its own
- do not fall back to `--dangerously-skip-permissions` to get past a denial — a denial inside is P-39 working; widen the role's `tools:` line if the role needs the tool, and say why in the commit
- do not read the budget from the worker's REPORT and write it into `budget.json`; the harness's number is the one that cannot be remembered wrongly (P-17c)
