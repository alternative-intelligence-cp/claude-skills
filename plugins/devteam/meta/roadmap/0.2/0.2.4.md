# 0.2.4 — wiring the sandbox into the pipeline: rules, skills, templates, permissions, docs — PLANNED

> The mechanism exists after 0.2.3. This subcycle makes the pipeline run on
> it: the rules that change, the skills that dispatch and promote, the
> charter row that says which containment a project has, the grant that
> shrinks, and the documents that must stop describing the guard as the
> mechanism. It is many small edits, and the discipline is that every one
> of them cites the measured failure it answers, because a rule without its
> reason is a rule the next reader litigates.

## 2. Decisions

L-3, L-6, L-7, L-10 apply. Local:

- **L-4.1 — a charter constraint row `Containment` with values `structural`
  and `guard-only`, set by `setup` from the probe, never assumed.** *Why:*
  the design's coverage now depends on an external variable (a kernel
  setting) that nobody inside a run can see; P-10b's own closing paragraph
  says such a dependency must be stated and its failure made loud. A project
  that says `structural` on a machine whose probe fails is `BLOCKED` at
  `run` startup, with the probe's table printed. *Declined:* silent
  degradation to the guard (the failure this pipeline has spent the most
  findings on is a check that quietly under-covers).
- **L-4.2 — `guard-only` is cycle 0.1's behaviour, kept whole, and its
  documentation says exactly which findings it leaves open** (F-80, F-121,
  F-71 and the shared-index class). *Why:* macOS, Windows, and Linux hosts
  without user namespaces exist, and a pipeline that refuses to run there
  loses the users who would report the entry-condition findings this project
  has never had enough of.
- **L-4.3 — rules are superseded by new numbers; the old text stays** (P-23).
  P-10b → P-10c, P-12b → P-12c, P-14 gains a fourth signal by a new rule
  rather than an edit, P-38 → P-38b. Two new rules, written here as
  `P-<containment>` and `P-<promotion>`: their numbers are allocated when
  they are written, never reserved in a plan — the plugin's self-check
  reports a cited rule that `PROTOCOL.md` does not declare, and it is right to.

## 3. The work

### 3.1 `PROTOCOL.md`

- **`P-<containment>` — a worker's writes land in a sandbox and reach the
  host only through promotion.** State what is contained (the filesystem, the index,
  the history), what is not (the network — L-4, with the accepted risk in
  the rule's text), and the measured failures it answers: F-80 (the manager
  used the unjudged heredoc form all run), F-121 (the refusal message
  cannot reach the case that matters), F-17, F-66, F-71, F-73, F-81 and the
  worker's half of F-135 (the shared index and history). **State the
  residual in the rule's own text**: the manager and supervisors remain
  host-side and share one index, and F-129 and the other half of F-135 are
  not closed by it (`../README.md` §2). Cite `test_sandbox.py` as the
  control that proves it.
- **`P-<promotion>` — promotion is serialised, gated by the declared scope,
  and never automatic.** The finding classes from 0.2.2 §3.2, the lock, the rule that
  an uncommitted remainder is evidence and not work, and L-2.2 (cite by
  subject).
- **P-10c supersedes P-10b.** Inside a sandbox the write form is free —
  `Write`, `Edit`, a redirect, a heredoc, an interpreter — because nothing
  judges it and nothing needs to; on the host (the manager, a `guard-only`
  project) P-10b's text still applies. Keep P-10b's paragraph about the
  ambient instruction: it is still true for the host and it is the clearest
  statement of "coverage depends on an external variable" in the file.
- **P-12c supersedes P-12b.** History is shared **at promotion**, not
  during work: inside an overlay, `--amend`, `reset`, `rebase` and `stash`
  act on the worker's own copy and above the base are permitted; the gate
  refuses a rewrite below the base (0.2.2 L-2.3). On the host, P-12b's
  prohibition stands for every host-side actor and the guard still enforces
  it. State that CONSOLIDATION 8b's mechanism is **narrowed** by this rule
  to host-side actors, and that its trigger is unchanged.
- **P-14b — liveness has a fourth signal, the sandbox file** (0.2.3 §3.5),
  read after the three P-14 names, and its two readings (live pid → not
  stale; dead pid with a non-empty upper → inspect, do not discard).
- **P-38b supersedes P-38** in one respect: the grant splits into
  *outward-facing* (withheld by name, applied inside as `--disallowedTools`)
  and *filesystem-shaped* (structural under `structural`, and under
  `guard-only` exactly as P-38 had it). Cite F-30, F-64, F-76, F-100 as the
  cost of the old shape.

### 3.2 Skills

**`run`** — §1.5 pins the sandbox harness's own version beside the plugin
commit (it is part of the command); §1 gains a startup check: charter says
`structural` → `sandbox_probe.py` must exit 0, else `BLOCKED` with the
table. §3's recovery table gains the sandbox-file column and the two
readings. §5's dispatch template gains `CONTAINMENT: structural | guard-only`
and `SANDBOX-ROOT: <abs>` (so a supervisor never guesses either). §6, on a
report: `check_report` now also reports `budget-mismatch` / `model-mismatch`
— name them in the table of what to do. §9b (removing something created in
error): under `structural` the manager's own writes are still host-side and
this section is unchanged; say so, because a reader will wonder.

**`supervise`** — §4 is the big one. Replace step 3 with a role table:

| Role | Dispatched by | Writes land |
|---|---|---|
| implementer, tester, documenter | `sandbox.py dispatch` in the background (0.2.3 §3.4) | the worker's overlay; promoted by you after its report |
| verifier, auditor, reviewer, researcher | `Agent` tool, as before | nowhere; a verifier or auditor that must mutate uses `sandbox.py exec` |

Then the sequence: open → heartbeat with the sandbox id → dispatch → on
exit read `meta/report.txt` → `check_report` on it (against the overlay's
task file: `sandbox.py` exposes `meta/taskfile.md`, extracted with the
bundle) → `promote --dry-run` → verify (a fresh verifier, against the
**promoted** tree — nothing is verified in an overlay that is about to be
discarded) → `promote` → tick the step. The two-attempt rule (P-20c) is
unchanged; a re-dispatch opens a **new** sandbox from the new base; the old
one is `close --keep` for the record and closed at task end. §6's close
checklist: every sandbox for the task closed, `.sandbox` file rewritten to
`exited`, no lock held. §7 (stopping): a stopped task's open sandboxes are
kept, not closed, and the report names their ids — the successor reads
them (this is P-27b applied to sandboxes).

**`work`** — §1: the dispatch carries `CONTAINMENT:`; under `structural`,
"you are inside a sandbox at the repository's own path; nothing outside it
exists; nothing you do reaches the host until your supervisor promotes it".
§2: the scope check stays (the guard warns early, L-6) and is reworded:
writing outside scope is refused by the guard *and* would be refused at
promotion. §4: P-10c — the write form is free inside. §5: cite commits by
subject, never by hash (L-2.2), with the reason; `check_scope` runs inside
against the overlay's own commits exactly as before. §6: the REPORT's
`budget:` and `model:` are cross-checked against the harness (L-3.2) — say
so, so a worker does not invent precision.

**`verify`** — replace "Where a mutation goes" with `sandbox.py exec`
(0.2.3 §3.7); the rest of the discipline is unchanged. Note that a
verifier runs against the promoted host tree, never inside a worker's
overlay.

**`audit`** — the same replacement where it tells an auditor how to try
something.

**`setup`** — §2: the grant is generated from the new `PERMISSIONS.md`
template with the split; the supervisor's `Bash(python3 …/sandbox.py:*)`
entry is added with its reason. §3: after proving the guard fires, **prove
the sandbox contains**: `sandbox_probe.py` → 0; then one `exec` on the
freshly scaffolded project that writes to a literal absolute path outside
it and prints `No such file or directory`. The charter's `Containment` row
is written from the probe's exit code, and the skill says what
`guard-only` leaves open (L-4.2), in the row's own comment.

**`resume`** — §3–§4: the sandbox files are part of "what the tree holds";
a kept sandbox with a non-empty upper is work a predecessor did not
promote, listed in the report before anything is re-dispatched.

**`status`** — one line per open sandbox from the `.sandbox` files.
