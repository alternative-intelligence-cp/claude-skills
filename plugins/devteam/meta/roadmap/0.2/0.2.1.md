# 0.2.1 — the harness: overlay, namespaces, and the controls that prove containment — PLANNED

> One script, `scripts/sandbox.py`, that opens a per-worker copy-on-write
> view of the repository inside a user and mount namespace, runs a command
> in it under `bwrap`, and records what happened. Its control is the point:
> a sandbox that has never refused has not been shown to contain anything.

## 2. Decisions

L-1, L-3, L-4 apply. Local:

- **L-1.1 — Python, not shell.** *Why:* every other shipped mechanism is a
  Python script with a Python control, `run_controls.py` discovers controls
  by that convention, and the harness's mount plan is data that a test has
  to inspect. The spec's bash harness is the reference, not the product.
- **L-1.2 — the whole repository is the overlay's lower layer, `.git`
  included** (spec §6.5). Scope is enforced at promotion (0.2.2) and warned
  about inside by the guard (L-6). *Declined:* per-scope binds (`../README.md` §7).
- **L-1.3 — the sandbox root is outside the repository:**
  `${DEVTEAM_SANDBOX_ROOT:-${TMPDIR:-/tmp}}/devteam-sandbox/<project-hash>/<id>/`.
  *Why:* an upper directory inside its own lower directory is undefined
  behaviour for overlayfs, and a sandbox directory inside the tree would be
  a foreign write to every check. `<project-hash>` is the first 12 hex of
  `sha256` of the repository's real path, so two projects never share a root.
- **L-1.4 — the toolchain binds come from the environment pin.** The charter
  names the interpreter and tools (P-33, `devteam/.run/env/<id>/`); the mount
  plan read-binds the directories those resolve to (`command -v python3` →
  its prefix; the plugin root; `~/.local/bin/claude`). *Why:* one home — the
  pin already says what the worker runs, so the sandbox binds exactly that.
  `MEASURED`: on this machine `python3` is a venv at
  `~/Workspace/SYSTEM/PY_ENV/bin/python3` and would be absent from a sandbox
  that bound only `/usr`. *Declined:* binding the whole home read-only (leaks
  every credential the environment was cleared to hide).

## 3. The work

### 3.1 `scripts/sandbox.py`

Subcommands. Every one prints one line per action it took, because the
supervisor reads this output and a silent success is indistinguishable from
a silent failure.

**`open --repo <abs> --task T-n [--step S-m] [--id <id>]`**
- refuses unless `sandbox_probe.py` would exit 0 (call it as a module; do not
  duplicate its rows)
- creates `<root>/<id>/{upper,work,merged,home,meta}`; `<id>` defaults to
  `T<n>-S<m>-<HHMMSS>`
- records `meta/base.sha` = `git -C <repo> rev-parse HEAD` **on the host,
  before anything enters** (spec §3.4 — this is the reference every later
  diff is taken against, and `HEAD` inside the overlay is the worker's to
  move)
- writes `meta/plan.json`: the repo path, the id, the task, the base, the
  list of read-only binds (L-1.4), the environment allowlist (3.3), the
  command (filled by `run`), timestamps
- prints `opened <id> base <sha> at <root>/<id>`

**`run <id> [--timeout <s>] -- <cmd...>`**
- composes spec §5: `unshare --user --map-root-user --mount` → inside, mounts
  the overlay with `lowerdir=<repo>,upperdir=<root>/<id>/upper,workdir=…/work`
  onto `…/merged` → `bwrap` with the arguments in 3.2 → `<cmd>`
- **runs the extraction (0.2.2 §3.1) inside the same namespace after `<cmd>`
  exits, before the namespace does** (spec §3.3). In this subcycle the
  extraction is a stub that copies `git -C <merged> status --porcelain -uall`
  to `meta/status.txt`; 0.2.2 replaces the stub
- tees `<cmd>`'s stdout and stderr to `meta/stdout.txt` and `meta/stderr.txt`
  and passes stdout through, so a caller that wants the worker's final message
  reads it either way
- writes `meta/exit.txt` with the exit code and `meta/timing.txt` with start,
  end and duration
- exits with `<cmd>`'s exit code; `125` if the sandbox itself failed to set
  up (the caller must be able to tell "the worker failed" from "there was no
  worker")

**`exec --repo <abs> [--keep] -- <cmd...>`**
- `open` + `run` + `close` in one, no task, no extraction beyond `status.txt`;
  a throwaway overlay for a verifier's mutation or an auditor's experiment.
  This is what replaces the scratch-directory recipe in `verify` §"Where a
  mutation goes" (F-100): the whole tree is mutable and none of it survives

**`status <id>`** — prints the plan's task, step, base, and whether a process
is alive on the sandbox (`meta/pid` written by `run`, checked with
`os.kill(pid, 0)`), and the last line of `meta/stderr.txt`. 0.2.3 makes this
the fourth liveness signal.

**`close <id> [--keep]`** — removes `<root>/<id>` unless `--keep`, which
leaves it for a post-mortem and prints the path. Refuses while `status` says
alive.

### 3.2 The `bwrap` arguments — each with the reason it is there

```
--unshare-user --unshare-pid --unshare-ipc --unshare-uts
                                   isolation; NOT --unshare-net (L-4)
--cap-drop ALL                     what the harness's own sandbox does
                                   (`../README.md` §4.2); bwrap also sets
                                   no-new-privileges on its own
--die-with-parent --new-session   spec §6.2, §6.3: no orphaned builds holding
                                   the overlay busy, no TIOCSTI into the
                                   parent terminal
--ro-bind /usr /usr
--ro-bind-try /bin /bin  --ro-bind-try /sbin /sbin
--ro-bind-try /lib /lib  --ro-bind-try /lib64 /lib64
--ro-bind-try /etc /etc            spec §6.4: -try, because merged-/usr
                                   systems symlink these and --ro-bind aborts
--proc /proc --dev /dev
--tmpfs /tmp                       scratch inside is ephemeral
--tmpfs <HOME>                     then populated by 0.2.3 (credentials copy)
--bind <merged> <repo>             L-3: the SAME absolute path as the host repo
--ro-bind <plugin root> <plugin root>
--ro-bind <each toolchain prefix> <same>      L-1.4
--chdir <repo>
--clearenv                         spec §4: never the host environment
--setenv PATH  <from the pin>
--setenv HOME  <HOME>
--setenv LANG  C.UTF-8
--setenv TMPDIR /tmp
--setenv DEVTEAM_SANDBOX <id>      so the guard and the worker know where they are
```

`HOME` inside is a path that does not exist on the host (`/home/devteam-worker`),
so nothing a worker does under `~` can coincide with a host path.

### 3.3 The environment allowlist is data, not code

`meta/plan.json` carries `env: {PATH, HOME, LANG, TMPDIR, DEVTEAM_SANDBOX}`
and 0.2.3 adds the credential and git-identity variables. `run` sets exactly
that map and nothing else. A control asserts that `SSH_AUTH_SOCK`,
`GH_TOKEN`, `GITHUB_TOKEN`, `ANTHROPIC_API_KEY` (unless 0.2.3 chose it) and
every `GIT_*` from the host are absent inside — by running `env` inside and
diffing against the plan.

### 3.4 `test_sandbox.py` — the control

Structure copied from `test_guard.py`: a list of cases, each `(name,
command-inside, expectation)`, run through the real harness against a
throwaway repository built in the scratchpad; the last line reports
`sandbox: N cases, M false-positive controls (P%), green`. **More than a
third of the cases are false-positive controls** (P-35), because a sandbox
that breaks a legitimate build is one somebody switches off.

Skip with exit `2` and one line naming the reason when `sandbox_probe.py`
does not exit 0 — a control that cannot run must say so, never pass.

Cases, at minimum, from spec §7b with the additions the run's findings ask
for. Every "blocked" case asserts **both** that the command failed **and**
that the host is byte-identical (`sha256sum` of every file under the repo
before and after, `.git` included):

| Must be BLOCKED | Assert |
|---|---|
| `echo x > /home/<user>/elsewhere/f` (a host path outside the repo) | stderr contains `No such file or directory`, **not** `Permission denied` — a permission error means DAC was built, not structure (spec S-4) |
| `../../` traversal from the repo to a host path | same |
| `ln -s /etc/passwd <repo>/link; echo x > <repo>/link` | the write lands in `upper` as a symlink target inside the overlay, or fails; the host `/etc/passwd` unchanged |
| `python3 - <<PY\nopen('/home/<user>/elsewhere/f','w')\nPY` | `FileNotFoundError` — **the interpreter case is the point of the exercise** (spec §7b) |
| `git -C /home/<user>/<another repo> commit --allow-empty -m x` | fails; that repo's `.git` unchanged |
| `git -C <repo> push` | fails on authentication or on no remote; never reaches the network with a credential (L-4) |
| writing under the plugin root | read-only |
| `sudo true` | fails — `bwrap` sets `PR_SET_NO_NEW_PRIVS`, so setuid does nothing, and `--cap-drop ALL` removes the rest; assert the failure, do not reason about which flag caused it |
| `mount`, `umount` inside `bwrap` | fail |
| `kill -9 1` from inside | PID 1 inside is `bwrap`'s init; the host is untouched |

| Must be ALLOWED | Assert |
|---|---|
| write, create, delete anywhere under `<repo>` | lands in `upper`; host unchanged |
| `git -C <repo> add -A && git commit -m x` | succeeds; host `.git` unchanged; `meta/status.txt` reflects it |
| `git -C <repo> commit --amend` | succeeds inside — it is the worker's own history now; 0.2.2 decides what promotion does with it |
| `rm -rf <repo>/build/` | succeeds; upper shows the whiteouts |
| `python3 -c "open('<repo>/x','w').write('y')"` | lands in `upper` — the same call that is blocked outside |
| `python3 -m pytest` on the throwaway project | runs; exit code passed through |
| reading anything under `/usr`, `/etc`, the plugin root, the repo | works |
| a 2 GiB file written under the repo | lands in `upper` — the spec's sizing gotcha, sized for disk not tmpfs |
| `cat /proc/self/uid_map` | not the host's identity map |
| a command that exits `3` | `run` exits `3`; `meta/exit.txt` says `3` |
| `sleep 1; echo done` under `--timeout 5` | `done` |
| `sleep 10` under `--timeout 2` | killed; `run` exits `124`; no process remains (`--die-with-parent`) |

And the two known-answer cases first (L-0.2): a known-contained write and a
known-allowed one, before anything interesting.

## 6. Do not

- do not bind the host `HOME` or any part of it read-only "for convenience" —
  the allowlist is the mechanism, and one convenience bind reintroduces every
  credential
- do not compute anything from `upper/` (spec §6.1); only the merged view is
  a filesystem
- do not add `--unshare-net` (L-4) — record the temptation under `## Findings`
  if a case seems to want it
- do not make the control pass by weakening an assertion; a case that cannot
  be made to pass is a finding about the design, recorded and escalated
