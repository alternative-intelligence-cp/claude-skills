## 2. Decisions

L-1, L-3, L-4 apply. Local:

- **L-1.1 — Python, not shell.** *Why:* every other shipped mechanism is a
  Python script with a Python control, `run_controls.py` discovers controls
  by that convention, and the harness's mount plan is data that a test has
  to inspect. The spec's bash harness is the reference, not the product.
- **L-1.2 — the whole repository is the overlay's lower layer, `.git`
  included** (spec §6.5). Scope is enforced at promotion (0.2.2) and warned
  about inside by the guard (L-6). *Declined:* per-scope binds (`../README.md` §7).
- **L-1.3 — the sandbox root is outside the repository:**
  `${DEVTEAM_SANDBOX_ROOT:-${TMPDIR:-/tmp}}/devteam-sandbox/<project-hash>/<id>/`.
  *Why:* an upper directory inside its own lower directory is undefined
  behaviour for overlayfs, and a sandbox directory inside the tree would be
  a foreign write to every check. `<project-hash>` is the first 12 hex of
  `sha256` of the repository's real path, so two projects never share a root.
- **L-1.4 — the toolchain binds come from the environment pin.** The charter
  names the interpreter and tools (P-33, `devteam/.run/env/<id>/`); the mount
  plan read-binds the directories those resolve to (`command -v python3` →
  its prefix; the plugin root; `~/.local/bin/claude`). *Why:* one home — the
  pin already says what the worker runs, so the sandbox binds exactly that.
  `MEASURED`: on this machine `python3` is a venv at
  `~/Workspace/SYSTEM/PY_ENV/bin/python3` and would be absent from a sandbox
  that bound only `/usr`. *Declined:* binding the whole home read-only (leaks
  every credential the environment was cleared to hide).

## 3. The work

### 3.1 `scripts/sandbox.py`

Subcommands. Every one prints one line per action it took, because the
supervisor reads this output and a silent success is indistinguishable from
a silent failure.

**`open --repo <abs> --task T-n [--step S-m] [--id <id>]`**
- refuses unless `sandbox_probe.py` would exit 0 (call it as a module; do not
  duplicate its rows)
- creates `<root>/<id>/{upper,work,merged,home,meta}`; `<id>` defaults to
  `T<n>-S<m>-<HHMMSS>`
- records `meta/base.sha` = `git -C <repo> rev-parse HEAD` **on the host,
  before anything enters** (spec §3.4 — this is the reference every later
  diff is taken against, and `HEAD` inside the overlay is the worker's to
  move)
- writes `meta/plan.json`: the repo path, the id, the task, the base, the
  list of read-only binds (L-1.4), the environment allowlist (3.3), the
  command (filled by `run`), timestamps
- prints `opened <id> base <sha> at <root>/<id>`

**`run <id> [--timeout <s>] -- <cmd...>`**
- composes spec §5: `unshare --user --map-root-user --mount` → inside, mounts
  the overlay with `lowerdir=<repo>,upperdir=<root>/<id>/upper,workdir=…/work`
  onto `…/merged` → `bwrap` with the arguments in 3.2 → `<cmd>`
- **runs the extraction (0.2.2 §3.1) inside the same namespace after `<cmd>`
  exits, before the namespace does** (spec §3.3). In this subcycle the
  extraction is a stub that copies `git -C <merged> status --porcelain -uall`
  to `meta/status.txt`; 0.2.2 replaces the stub
- tees `<cmd>`'s stdout and stderr to `meta/stdout.txt` and `meta/stderr.txt`
  and passes stdout through, so a caller that wants the worker's final message
  reads it either way
- writes `meta/exit.txt` with the exit code and `meta/timing.txt` with start,
  end and duration
- exits with `<cmd>`'s exit code; `125` if the sandbox itself failed to set
  up (the caller must be able to tell "the worker failed" from "there was no
  worker")

**`exec --repo <abs> [--keep] -- <cmd...>`**
- `open` + `run` + `close` in one, no task, no extraction beyond `status.txt`;
  a throwaway overlay for a verifier's mutation or an auditor's experiment.
  This is what replaces the scratch-directory recipe in `verify` §"Where a
  mutation goes" (F-100): the whole tree is mutable and none of it survives

**`status <id>`** — prints the plan's task, step, base, and whether a process
is alive on the sandbox (`meta/pid` written by `run`, checked with
`os.kill(pid, 0)`), and the last line of `meta/stderr.txt`. 0.2.3 makes this
the fourth liveness signal.

**`close <id> [--keep]`** — removes `<root>/<id>` unless `--keep`, which
leaves it for a post-mortem and prints the path. Refuses while `status` says
alive.

### 3.2 The `bwrap` arguments — each with the reason it is there

> **Corrected 2026-09-07 by 0.2.0, which measured this composition.** Two
> changes, both in the list below rather than in this note, and both from
> 0.2.0's `## Findings`: `--uid` and `--gid` are added beside `--unshare-user`
> because without them the worker is root and the CLI refuses to start, and
> the toolchain binds resolve symlinks because `claude` is one. 0.2.0's own
> §3.3 composition used `--ro-bind / /` and is **not** a model for this list —
> read it for the flags it proves, not for its mount plan.

`HOME` inside is a path that does not exist on the host (`/home/devteam-worker`),
so nothing a worker does under `~` can coincide with a host path. This works
because the list above builds a root out of named binds inside bwrap's own
tmpfs; it would **not** work under a `--ro-bind / /` root, where bwrap cannot
create a mount point it was not given (`0.2.0` measured
`Can't mkdir /home/probe: Read-only file system`). That is the reason to keep
this list restrictive rather than a tidier `--ro-bind / /` plus exclusions.

The worker's `HOME` must be writable and will hold, measured in 0.2.0 §3.3:
`.claude.json`, `.claude/{backups,projects/<slug>,session-env,sessions,shell-snapshots}`
and `.cache/claude-cli-nodejs/<slug>/`. The transcript of the worker's own run
lands in `.claude/projects/<slug>/<session-id>.jsonl` — which is where a
post-mortem reads what a worker actually did, so `close --keep` should keep it.

### 3.3 The environment allowlist is data, not code

`meta/plan.json` carries `env: {PATH, HOME, LANG, TMPDIR, DEVTEAM_SANDBOX}`
and 0.2.3 adds the credential and git-identity variables. `run` sets exactly
that map and nothing else. A control asserts that `SSH_AUTH_SOCK`,
`GH_TOKEN`, `GITHUB_TOKEN`, `ANTHROPIC_API_KEY` (unless 0.2.3 chose it) and
every `GIT_*` from the host are absent inside — by running `env` inside and
diffing against the plan.

Structure copied from `test_guard.py`: a list of cases, each `(name,
command-inside, expectation)`, run through the real harness against a
throwaway repository built in the scratchpad; the last line reports
`sandbox: N cases, M false-positive controls (P%), green`. **More than a
third of the cases are false-positive controls** (P-35), because a sandbox
that breaks a legitimate build is one somebody switches off.

Skip with exit `2` and one line naming the reason when `sandbox_probe.py`
does not exit 0 — a control that cannot run must say so, never pass.

Cases, at minimum, from spec §7b with the additions the run's findings ask
for. Every "blocked" case asserts **both** that the command failed **and**
that the host is byte-identical (`sha256sum` of every file under the repo
before and after, `.git` included):

| Must be BLOCKED | Assert |
|---|---|
| `echo x > /home/<user>/elsewhere/f` (a host path outside the repo) | stderr contains `No such file or directory`, **not** `Permission denied` — a permission error means DAC was built, not structure (spec S-4) |
| `../../` traversal from the repo to a host path | same |
| `ln -s /etc/passwd <repo>/link; echo x > <repo>/link` | the write lands in `upper` as a symlink target inside the overlay, or fails; the host `/etc/passwd` unchanged |
| `python3 - <<PY\nopen('/home/<user>/elsewhere/f','w')\nPY` | `FileNotFoundError` — **the interpreter case is the point of the exercise** (spec §7b) |
| `git -C /home/<user>/<another repo> commit --allow-empty -m x` | fails; that repo's `.git` unchanged |
| `git -C <repo> push` | fails on authentication or on no remote; never reaches the network with a credential (L-4) |
| writing under the plugin root | read-only |
| `sudo true` | fails — `bwrap` sets `PR_SET_NO_NEW_PRIVS`, so setuid does nothing, and `--cap-drop ALL` removes the rest; assert the failure, do not reason about which flag caused it |
| `mount`, `umount` inside `bwrap` | fail |
| `kill -9 1` from inside | PID 1 inside is `bwrap`'s init; the host is untouched |

| Must be ALLOWED | Assert |
|---|---|
| write, create, delete anywhere under `<repo>` | lands in `upper`; host unchanged |
| `git -C <repo> add -A && git commit -m x` | succeeds; host `.git` unchanged; `meta/status.txt` reflects it |
| `git -C <repo> commit --amend` | succeeds inside — it is the worker's own history now; 0.2.2 decides what promotion does with it |
| `rm -rf <repo>/build/` | succeeds; upper shows the whiteouts |
| `python3 -c "open('<repo>/x','w').write('y')"` | lands in `upper` — the same call that is blocked outside |
| `python3 -m pytest` on the throwaway project | runs; exit code passed through |
| reading anything under `/usr`, `/etc`, the plugin root, the repo | works |
| a 2 GiB file written under the repo | lands in `upper` — the spec's sizing gotcha, sized for disk not tmpfs |
| `cat /proc/self/uid_map` | not the host's identity map |
| a command that exits `3` | `run` exits `3`; `meta/exit.txt` says `3` |
| `sleep 1; echo done` under `--timeout 5` | `done` |
| `sleep 10` under `--timeout 2` | killed; `run` exits `124`; no process remains (`--die-with-parent`) |

And the two known-answer cases first (L-0.2): a known-contained write and a

## Findings

Recorded as they arrived, 2026-09-07. Ordered by what they change, not by when
they turned up. Every number below has the command that produced it beside it.

- **§3.2's mount list, built exactly as written, lets a write to a host path
  SUCCEED — silently, into a tmpfs that evaporates.** This is the finding of
  the subcycle and it was found by a case failing, not by reading.
  `bwrap` synthesises a directory for every mount point it is handed, and
  those directories live in its own root tmpfs and are **writable**. Binding
  the toolchain (L-1.4) under the invoking user's home therefore materialises
  `~`, `~/Workspace` and `~/Workspace/SYSTEM`; binding the plugin at its host
  path (§3.2) materialises `~/Workspace/REPOS` and the repository root above
  it. `MEASURED` on the composition as specified:

  ```
  $ ... run smoke1 -- sh -c 'echo escaped > ~/devteam-sandbox-escape-proof.txt'
  run smoke1: exit 0 after 0.0s                     <- SUCCEEDED
  $ ls ~/devteam-sandbox-escape-proof.txt
  ls: cannot access ...: No such file or directory  <- and wrote nothing, anywhere
  $ ... run -- sh -c 'mkdir -p ~/Workspace/REPOS/fake && echo x > ~/Workspace/REPOS/fake/f'
  MKDIR ok                                          <- a whole phantom sibling repository
  ```

  The host is safe throughout — the overlay never stopped working. What fails
  is the **worker's model of what happened**: it is told a write succeeded to
  a path that will never hold it, and every step it takes afterwards on that
  basis is wrong. A silent false success is worse than a refusal, because a
  refusal is a thing a worker can report.

  **The fix is one entry, and its position is the whole of it:**
  `--remount-ro /`, last, after every bind. `--remount-ro` touches only the
  mount it names, so `/tmp`, the worker's `HOME` and the repository bind stay
  writable while bwrap's scaffolding does not. Re-measured after:

  ```
  sh: 1: cannot create ~/devteam-escape.txt: Read-only file system
  mkdir: cannot create directory '~/Workspace/REPOS/fake': Read-only file system
  ```

  **The part worth carrying forward is how nearly this was missed.** §3.4's
  own example for the case is `echo x > /home/<user>/elsewhere/f`, and
  `elsewhere` is a component nothing synthesises, so that path returns
  `No such file or directory` and **the case would have passed with the hole
  wide open**. The case only fails when the target sits *directly* in a
  synthesised directory. This is the P-35b class again and the third instance
  in three subcycles: an instrument answering a question adjacent to the one
  asked. The control now uses a target directly in a synthesised directory as
  its known-contained case (L-0.2), so the strict form runs first every time.

- **A sandbox built to §3.2's list has no DNS, so a worker inside it cannot
  reach the model API at all.** `/etc/resolv.conf` on this machine — and on
  any systemd-resolved machine — is a symlink to
  `/run/systemd/resolve/stub-resolv.conf`, which `--ro-bind-try /etc /etc`
  leaves dangling. `MEASURED`, twice, differing only in that bind:

  ```
  resolv: ; exists=no        dns FAIL      (the list as written)
  resolv-target: /run/systemd/resolve/stub-resolv.conf; readable: yes   dns ok
  ```

  This would have surfaced in 0.2.3 as an authentication failure and been read
  as a credentials problem. The mount plan now resolves `/etc/resolv.conf` at
  `open` and binds the directory it actually points into, when that is outside
  `/etc` — so it holds on a machine that points it somewhere else, rather than
  hardcoding systemd's path. `fp-dns-resolves` is a false-positive control:
  L-4 keeps the network shared **on purpose**, and a sandbox that breaks DNS
  breaks the worker.

- **Binding the pinned toolchain is not enough; its `bin` has to be on `PATH`,
  and the two are different directories.** L-1.4 was read as "bind what the
  tools resolve to". Done that way, `python3` inside resolved to
  `/usr/bin/python3.12` — a working interpreter that can import nothing the
  project pinned — because the venv's own `bin` was bound but never named in
  `PATH`. The pin would have been silently not honoured, which reads as a
  broken project rather than a broken sandbox. `MEASURED` after the fix:
  `sys.prefix` inside is the venv `pin.txt` names, and `python3 -m pytest
  --version` → `pytest 9.0.2`, the version in the pin. The rule now written
  into the code: **`PATH` carries the directory a tool is NAMED from, never
  the one it resolves to** — `claude` resolves to a versioned *file* whose
  directory holds nothing else, and putting that on `PATH` is how a plausible
  entry becomes a useless one.

- **`argparse.REMAINDER` turned a flag into the program to execute.**
  `run <id> --timeout 2 -- sleep 10` ran a command called `--timeout`:
  `/devteam-cmd.sh: 5: exec: --timeout: not found`. REMAINDER starts
  collecting at the first token argparse does not recognise, which is the
  positional *before* the flags. The command is now split off on the first
  standalone `--` before argparse is called at all, which is what the §3.1
  grammar says and cannot mis-parse. Recorded because the failure mode is
  quiet: a mistyped flag becomes a program, and the sandbox faithfully reports
  that the program was not found.

- **The symlink case §3.4 specifies cannot fail, so it proves nothing.**
  `ln -s /etc/passwd <repo>/link; echo x > <repo>/link` is refused with
  `Permission denied` — and `MEASURED`, the identical command with **no
  sandbox at all** is refused with the identical message, because
  `/etc/passwd` is root-owned and the invoking user is not root. The case
  tests Unix file permissions and would pass with the sandbox removed.
  Replaced with a symlink to a host file this user **owns and can write** (the
  sibling repository's `tracked.txt`), which is refused inside and, measured
  unsandboxed, succeeds and clobbers the file. That version distinguishes.
  An allowed twin was added beside it — a symlink followed *within* the
  overlay must still work (spec §7b).

- **"stderr contains `No such file or directory`" is an assertion about which
  shell the worker used.** `MEASURED`: `dash` words ENOENT as
  `Directory nonexistent`, `bash` as `No such file or directory`, Python as
  `FileNotFoundError`. And there are now **two** structural refusals, not one:
  ENOENT where nothing was bound, EROFS where bwrap's own root was. Neither is
  DAC, which is what spec S-4 actually cares about. So the control asserts the
  **errno** where it can reach it (the interpreter case reads `errno=2`), and
  everywhere else asserts that the command failed and that the reason was
  **not** `Permission denied`. That is stricter than the prose assertion, not
  looser: the prose assertion passes on the wrong shell for the wrong reason.

- **§3.2's `--tmpfs <HOME>` contradicts §3.1 and §3.2's own next paragraph.**
  §3.1 has `open` create a `home/` directory in the sandbox root; §3.2 mounts
  a tmpfs over `HOME` instead, and then says the worker's transcript lands
  under `HOME` and "`close --keep` should keep it". A tmpfs cannot be kept.
  Built as §3.1 implies: `--bind <root>/<id>/home /home/devteam-worker`, a
  real directory, so `close --keep` leaves a readable post-mortem. 0.2.0's own
  working composition did the same.

- **`open` cannot seed the git identity, and `run` has to.** 0.2.0's finding
  says `sandbox.py open` seeds `user.name` and `user.email` into the overlay's
  repository config. At `open` there is no overlay — it is mounted by `run`,
  inside the namespace, and does not exist before or after. Nor can the config
  be written into `upper/` directly: overlayfs is file-granular, so an
  `upper/.git/config` **replaces** the lower one whole and would take the
  remotes with it. So `open` records the host's identity in `plan.json` and
  `run` applies it inside the namespace before the command, where writing it
  copies the real config up intact. Same effect, only place it can happen.

- **§3.5 asks for two things, and both rest on a wrong belief about
  `check_plugin.py`.** It has no "list it keeps of scripts a skill may
  reference" — `SCRIPT_REF` is a regex matched against the filesystem, so
  0.2.4's references to `${CLAUDE_PLUGIN_ROOT}/scripts/sandbox.py` resolve
  because the file exists, and there is nothing to add. And it does **not**
  report `uncontrolled-check` for `sandbox.py`: that rule keys on a `check_`
  filename prefix, exactly as 0.2.0's last finding recorded, so it never asked
  for `test_sandbox.py`. `MEASURED`: `check_plugin.py` → `clean` both before
  and after `test_sandbox.py` existed. The control was written regardless.
  **Not worked around here**: 0.2.0 assigned the widening of that rule to
  0.2.4, and widening it in passing would put the change where nobody is
  looking for it.

- **`--clearenv` is hiding more than a credential.** Dropping it in the
  mutation test showed the whole host environment arriving inside, including
  `CLAUDE_CODE_MESSAGING_SOCKET` and `CLAUDE_CODE_MESSAGING_TOKEN` — this
  harness's cross-session messaging credentials — alongside the planted
  `ANTHROPIC_API_KEY`, `GH_TOKEN`, `GITHUB_TOKEN` and `SSH_AUTH_SOCK`. A
  worker with those could message the owner's other live sessions. Worth
  saying plainly where the flag is documented in 0.2.4: the environment
  allowlist is not only about the model credential.

- **The control was mutation-tested; four mutations, four catches.** A control
  that cannot fail proves nothing, so `sandbox.py` was broken four ways and
  the suite re-run each time:

  | Mutation | What the control said |
  |---|---|
  | `--remount-ro /` removed | `FAIL known-contained-write: expected to be BLOCKED and the command SUCCEEDED` |
  | the repository bound instead of the overlay | 28 of 29 failed, including `the host repo changed on disk during this case` |
  | `--clearenv` removed | `FAIL fp-the-environment-is-the-allowlist: variables inside that the plan never declared: [...78 of them...]` |
  | the `timeout` prefix removed | `FAIL timeout-kills-a-long-command: exited 125, expected 124` |

  The last one is the reserved codes earning their keep: with no `timeout(1)`
  the Python backstop killed the process group before the namespace could
  record an exit status, and `125` — "there was no worker" — is the honest
  answer rather than a guess at what the worker would have returned.

- **The live proof (§4), in two halves, because one half is not a proof.**
  Run against a **literal absolute host path inside this repository**, from a
  sandbox opened on a throwaway repository elsewhere:

  ```
  ### (a) UNSANDBOXED, so the case can fail: the same command, no sandbox
  $ bash -c "echo escaped > <repo root>/SANDBOX-ESCAPE-PROOF.txt"

  run liveproof: exit 1 after 0.0s
  ```

  DAC; which one appears depends on whether the path's parent is a directory

  comment so the next reader is not surprised by it.

- **The session transcript's usage rows double- and triple-count, and the
  wrong sum agrees with the one anchor anyone has to check it against.** A
  subcycle's own token cost can be self-measured from
  `~/.claude/projects/<slug>/<session-id>.jsonl` without asking anybody, which
  is worth having because the percentage cannot be. But one API request is
  written to that file **once per content block** — text, thinking and each
  tool use — and every row repeats the whole message-level `usage` object.
  `MEASURED` on this session: 106 usage-bearing rows, `50` unique
  `requestId` values, up to three rows per request, the `usage` objects
  byte-identical across them.

  Summed by row: `15.3 M` cache read. Summed by request: `7.28 M`. **The
  inflated figure lands within 2% of 0.2.0's harness-reported `15.5 M`, and
  the inflated row count (106) within 2% of its 104 requests.** A reader
  checking the naive method against the only anchor available would have
  confirmed it. That is P-35b with the safety net removed: the wrong
  instrument did not merely fail to disagree with the truth, it agreed with
  it. Key on `requestId`. (`message.id` gives 51 — the extra is a synthetic
  error row carrying no request at all, which is itself a reason to prefer
  the request key.)

  One more, because it would silently attribute one session's cost to
  another: the session id is in the scratchpad path this harness hands each
  session, and **that is the identifier to use**. Picking the newest `.jsonl`
  by mtime, which is the obvious alternative, returns whichever session on
  the project wrote last — during a handoff, with two sessions alive, a coin
  flip. Both files here had the same minute stamp.

- **`close` removed the sandbox and left its project directory, once per
  run.** L-1.3 puts each project's sandboxes under a `<project-hash>`
  directory, and `close` removed only the sandbox inside it. The control
  builds a throwaway repository in a fresh temp directory every time, so every
  run minted a new hash and left an empty directory behind: nine of them under
  `/tmp` in one afternoon, `MEASURED` by listing it. `close` now `rmdir`s the
  parent — and `rmdir`, never `rmtree`, so it refuses while a sibling sandbox
  is still open. A leak of empty directories is the kind of thing nobody
  notices until a `/tmp` cleaner or an inode limit does.

- **The reserved exit codes are ambiguous with a command that genuinely
  returns them, and the ambiguity is resolved by a file rather than by hope.**
  `run` returns `125` for "the sandbox never set up" and `124` for the
  timeout, and a worker's own command may legitimately exit with either. The
  outer script writes `meta/exit.txt` only after `bwrap` has returned, and a
  mount failure writes `meta/setup-failed` instead, so the two are told apart
  by which file exists rather than by the number. A caller that needs
  certainty reads those files; the number is the convenience.

- **No case wanted `--unshare-net`, and the one that came closest wanted the
  opposite** (§6 asks for the temptation to be recorded). The DNS finding is
  it: the pull was toward making the network *work*, not toward severing it.
  L-4 stands unamended, and its trigger — a worker observed contacting
  anything but the model API — is untouched by anything measured here.

- **`git commit --amend` inside rewrote only the overlay's history, again,
  now through the shipped harness rather than a hand-built composition.**
  `fp-git-commit-amend` is a standing case: it commits, amends, reads back
  `amended by the worker` from the overlay's `git log`, and the suite then
  requires the host repository to be byte-identical including `.git`. That is
  `../README.md` §2's expensive class — F-71, F-73, F-81 and the worker half
  of F-135 — held by a control that runs on every `run_controls.py`.

- **P-35b is this cycle's dominant failure mode, not a run of bad luck, and
  0.2.2 should plan for it rather than be surprised by it.** Six instances in
  two subcycles, every one an instrument that answered a question adjacent to
  the one asked:

  | # | The instrument | What it said, and why it was wrong |
  |---|---|---|
  | 1 | 0.2.0 §3.3's first sandboxed run | the `work` skill was absent — three levels of shell quoting, not the sandbox |
  | 2 | `check_plugin.py`'s `uncontrolled-check` | `clean`, because the rule keys on a `check_` filename prefix and never asked |
  | 3 | 0.2.0's sibling-repository finding | measured on one composition, extended unmarked to one never run (struck by 0.2.0 after this subcycle ran the case) |
  | 4 | §3.4's contained-write example | its target's parent is a component nothing synthesises, so it returns ENOENT and passes with the hole open |
  | 5 | §3.4's planted-symlink case | `/etc/passwd` is refused identically with the sandbox and without it |
  | 6 | summing the transcript's usage rows | triple-counts, and the inflated total agrees with the only anchor to within 2% |

  **Not one of them was found by reading the instrument.** Every one was found
  by running it and putting the observed output beside the expected output —
  which is L-0.1, and it has now earned its cost six times. The pattern
  underneath them is worth naming for whoever writes 0.2.2's cases: an
  instrument fails silently exactly when its case is satisfied *by something
  other than the mechanism under test* — a shell's permissions, a filename
  convention, a path component, a duplicated log row. So the question to ask
  of every new case is not "does this pass?" but **"what else could make this
  pass?"**, and the cheapest answer is to run it once with the mechanism
  removed. Four mutations cost one command here and caught four real defects.
