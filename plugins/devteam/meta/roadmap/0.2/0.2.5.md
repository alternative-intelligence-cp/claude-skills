# 0.2.5 — manager rotation at every checkpoint, and reading at the point of use — PLANNED

> The one role that never resets is the one everything flows through, and
> the rule that makes it trustworthy (P-17, verbatim reports) is the rule
> that fills it: 897 KB of task files, roughly 230,000 tokens, passed upward
> verbatim on the first run, plus a record, a decision log and a question
> log re-read throughout. A manager cannot measure its own context, so the
> trigger must come from outside, and compaction is a copy of a copy. This
> is the item the owner named most valuable in the queue.

## 1. Where you are

0.2.4 is `DONE` and the pipeline runs on the sandbox; the harness now
measures every worker's tokens (0.2.3 L-3.2), which is what makes a manager's
own reading measurable for the first time. 0.2.0 §3.5 recorded whether a
message reaches a session whose turn has ended — **re-read it**; §3.2 below
depends on it.

Read: `docs/CONSOLIDATION.md` items 1 and 6 in full; `skills/resume/SKILL.md`
§0 (the incoming side already exists — this subcycle builds the outgoing

## 2. Decisions

L-8 applies. Local:

- **L-5.1 — the outgoing manager never spawns its successor.** *Why:* a
  session cannot start an interactive successor, and a headless successor
  cannot reach a `terminal` client; the successor is started by whoever
  owns the channel — a person, or a scheduler the operator runs. The
  outgoing side's whole job is to *become safely replaceable* and say so.
- **L-5.2 — the handoff is a live exchange when the outgoing session is
  reachable, and a reconstruction when it is not**, exactly as `resume` §0
  already says; this subcycle adds the file that tells the incoming session
  which case it is in. *Why:* the owner's stated practice, and the
  measurement it yields — every question asked is a defect in the record.
- **L-5.3 — the periodic refresh (CONSOLIDATION 6) is the small set only:**
  width, the pinned environment, the live claims, the protected paths, the
  priority order, the client channel — re-read from the board header on
  every report. Everything else is re-read at the decision it governs.
  *Why:* re-reading a 34 KB charter on a timer is not affordable and not
  what makes the difference; a decision made with the governing text one
  screen above it is.

## 3. The work

### 3.1 The trigger and the outgoing side — `run` §7 and a new §7b

After a checkpoint is filed and committed (`ON-COURSE` or otherwise):

1. write `devteam/.run/session/handoff-ready`:
   ```
   session <id> checkpoint C-n at <iso>
   claims-in-flight: <T-n list or none>
   sandboxes-open: <ids or none>
   ```
2. append to `RECORD.md`: `rotation due (C-n): handoff-ready written; this
   session continues until the successor takes the lock`
3. tell the client, by the charter's channel: *"Rotation is due. Start a
   fresh session in this directory and run `/devteam:resume`; keep this one
   open until it reports it holds the lock."* For channel `none`, the line
   goes into the record and the checkpoint only; for `session <name>`, it
   is sent there.
4. **keep working.** Nothing stops; the loop continues until the successor
   takes the lock. Stopping would idle the pipeline on a human's schedule,
   which P-28 forbids for a single task and forbids doubly for all of them.

### 3.2 The incoming side — `resume` §0, extended

When `handoff-ready` exists and names another session:

1. `ListAgents` — is that session listed? If yes, message it per §0 as
   written (drive; ask only what the files could not say). If 0.2.0 §3.5
   found that a session whose turn has ended is **not** reachable, the skill
   says so in one sentence and proceeds to reconstruction; the outgoing
   session's §3.1 step 4 then matters more, because "keep working" is what
   keeps it reachable.
2. take the lock: board writer line, `.run/session/manager`, commit
   `board: writer <new id> (rotation from <old id>, C-n)`; write
   `writer handoff: <old> → <new>` in `RECORD.md`.
3. message the outgoing session: *"I hold the lock as of <commit>. Finish
   nothing further; end your turn."* — and the outgoing session's `run` §2
   says what it does on receiving that: one last record line, then it ends
   its turn and takes no further action on that project. **The guard
   enforces the rest**: its `devteam/` writes are refused from that commit
   on (P-13), which is the control for this whole mechanism.
4. remove `handoff-ready` (the manager may remove an untracked file it
   created — `run` §9b — and this one was created by its predecessor for
   exactly this reader; say so in the record line).
5. log every question that had to be asked as `record defect: the incoming
   session had to ask <what>` — one line each, under the day's entry. That
   list is the measurement.

### 3.3 The measurement that tunes the cadence

Two numbers per rotation, both from commands, recorded at the next
checkpoint under a `## Rotation` heading:

- **manager tokens since the last rotation** — the sum of the harness's
  `budget.json` figures is the *workers'* cost; the manager's own reading is
  the CLI's own usage for the session, which is available on this machine
  from the session's transcript metadata (`REASONED` — find where the
  harness records per-session usage and cite the path; if there is no
  observable, say so and count report bytes handled instead, which is
  countable: `wc -c` over the task files' execution records appended since)
- **questions asked at the handoff** — the count of `record defect` lines

The cadence is "every checkpoint" until three rotations exist; then the
checkpoint skill's §4 ("is the plan still right?") gains one question: is
the rotation cadence right, given those two numbers.

### 3.4 Reading at the point of use — `run` §6, §7, §8; `supervise` §4, §6

Add, at each named decision, the one line that re-opens what governs it:

| Decision | Re-read, then |
|---|---|
| on any report (`run` §6, first line) | the board header: width, pin, claims, protected paths, priority order, client channel (L-5.3) |
| classifying an escalation (`run` §8) | P-26's table, and the charter's priority order row |
| filing a checkpoint (`run` §7 → `checkpoint`) | the charter, in full — it is the checkpoint's subject, not background |
| closing a task (`supervise` §6) | the task's `Gate.` and `Verify.` lines, from the file, not from the dispatch you were given hours ago |
| accepting a step (`supervise` §4.6) | the step's line in the task file's §Steps |

Each line carries its reason in five words or fewer — *"your dispatch is
hours old"* — because the point of placing it here is that it is read at
the moment it applies (DESIGN §20b).

### 3.5 `reinject.py`

Unchanged in mechanism. Its block gains one line: *"If
`devteam/.run/session/handoff-ready` names another session, a rotation is
in progress — read `resume` §0 before touching the board."* A compacted
manager that has just been replaced must not re-take a lock it lost.

### 3.6 Controls

- `test_guard.py`: after a writer change on the board, a `devteam/` write
  carrying the old session id is refused, and one carrying the new is
  allowed (the P-13 control probably exists — extend it to the rotation
  commit form, and assert the refusal message names the rotation).
- `test_reinject.py`: the handoff line appears when the file names another
  session and not otherwise.
- A control for the `handoff-ready` file's grammar (it is parsed by
  `resume`; parse it in `check_refs` or a small function, and plant a
  malformed one).

## 6. Do not

- do not make rotation stop the loop — the outgoing session works until replaced
- do not add a token-count or wall-clock trigger; the checkpoint is the trigger (L-8), and the numbers in §3.3 are for deciding the cadence later
- do not summarise the record for the successor; the successor reads the record and asks (CONSOLIDATION 1: a summary is the copy-of-a-copy this replaces)
- do not have the outgoing session write a "handoff document" — the questions the successor asks are the handoff, and they are only useful because nobody pre-empted them
