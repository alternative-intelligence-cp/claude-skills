## 2. Decisions

L-5 applies. Local:

- **L-2.1 — extraction captures three things and labels them:** the
  committed work as a bundle, the uncommitted remainder as a patch, and the
  status listing. *Why:* a step is supposed to end committed (P-16); an
  uncommitted remainder is evidence of something — a death, a worker that
  stopped early, or post-commit scratch — and it must be visible without
  being promoted. *Declined:* one combined `git diff <base>` (spec S-5's
  form; it cannot tell committed from uncommitted, and the report check
  needs to).
- **L-2.2 — inside a sandbox, commits are cited by subject, never by
  hash.** *Why:* cherry-pick rewrites every hash at promotion. P-16's
  `- HEAD <subject>` form already anticipates that the hash is unknown at
  writing time; this extends it to "and will change". `check_report`
  resolves by subject today. *Cost:* a worker that wrote a literal hash into
  its execution record about an earlier step has written a stale claim;
  0.2.4 puts the rule in `work` §5 where the worker is standing.
- **L-2.3 — `--amend` inside the overlay is allowed above the base and
  refused below it.** *Why:* above the base the history is the worker's own
  and nobody else can see it; below the base it is the host's, and a bundle
  whose first-parent chain does not reach the base is a rewrite of shared
  history dressed as new work. This is P-12b made structural: the rule
  stays for the host, and inside it needs no rule.
- **L-2.4 — promotion holds one lock per repository:**
  `devteam/.run/locks/promote.lock`, `flock`ed. *Why:* two supervisors
  promoting at once race on the host `HEAD`; their scopes are disjoint
  (P-12) so the content cannot conflict, but the ref update can. The lock
  is held for the cherry-pick only.

## 3. The work

### 3.1 Extraction — replaces 0.2.1's stub, runs inside the namespace

After `<cmd>` exits and before `bwrap`'s namespace does, inside the same
`unshare` shell, against `<merged>`:

```
git -C <merged> bundle create <meta>/commits.bundle <base>..HEAD
    → meta/commits.bundle, or absent if HEAD == base (record "no commits")
git -C <merged> rev-list --first-parent <base>..HEAD
    → meta/commits.txt : one hash and subject per line, oldest first
git -C <merged> merge-base --is-ancestor <base> HEAD ; echo $?
    → meta/base-is-ancestor.txt : 0 or 1  (L-2.3's evidence)
git -C <merged> add -N . && git -C <merged> diff HEAD --binary
    → meta/uncommitted.patch  (the remainder; L-2.1)
git -C <merged> status --porcelain -uall
    → meta/status.txt
```

`-uall`, because `git status` collapses an untracked directory to its
prefix and 0.1 measured that turning a worker's new package into a
"foreign write" (DESIGN §20, `-uall fixes it`). `--binary`, so a patch of
a binary fixture survives.

> **Corrected as built — read the findings, not the block above.** The ORDER is
> wrong: `add -N` rewrites `??` as ` A`, so `status.txt` is taken **first**.
> `bundle create` **fails** rather than writing nothing when `HEAD == base`, so
> a commit count decides whether it is called. A sixth artifact,
> `meta/commit-paths.txt`, is recorded here rather than derived at promotion
> time, so `--dry-run` needs no fetch. And a file too large for
> `diff --binary` is named in `meta/uncommitted-oversize.txt` rather than
> diffed. Each has its measurement under `## Findings`.

Each step writes its exit code to `meta/extract.log`. An extraction failure
is `run` exit `126`, distinct from the worker's own exit and from setup's
`125`.

### 3.2 `sandbox.py promote <id> [--dry-run]`

Reads `meta/plan.json`, the bundle, `commits.txt`, `uncommitted.patch`,
`status.txt`, and the task file's `Scope.` (via `check_scope`'s parser).
Then, in this order, stopping at the first finding — one fault, one finding:

| Finding | Condition | Control plants |
|---|---|---|
| `promote-no-commits` | no bundle and an empty remainder | a worker that did nothing |
| `promote-history-rewrite` | `base-is-ancestor.txt` is `1` | an `--amend` of the base commit inside |
| `promote-foreign-subject` | a commit subject in `commits.txt` not of the form `T-n.S-m: …` (or `T-n: …` for a supervisor's close) matching this sandbox's task | a commit subject naming another task |
| `promote-out-of-scope` | `git diff-tree --no-commit-id --name-only -r` over the bundle's commits names a path outside `Scope.` ∪ `devteam/tasks/T-n.md` | a commit touching a neighbour's file |
| `promote-uncommitted` | `uncommitted.patch` non-empty | a worker that edited after its last commit |
| `promote-base-moved` | **not a finding** — host `HEAD` ≠ base is the normal case at width above one; recorded as a line, not a refusal | — |
| `promote-conflict` | cherry-pick stops | two sandboxes from the same base touching one path (which P-12 forbids — the control is the proof that the gate catches it anyway) |

`--dry-run` prints the findings and the would-be cherry-pick list and
touches nothing. The supervisor runs it first (0.2.4 puts that in
`supervise` §4).

> **Corrected as built.** `promote-conflict` is **not** in that table: the gate
> is pre-flight and a conflict is only discoverable by applying, so it is a
> runtime outcome and `--dry-run` says in its own words that it did not test
> for one. `promote-history-rewrite` fires on **anything but `0`**, not on `1`.
> `promote-uncommitted` reads `status.txt` as well as the patch. Six findings
> are added — `promote-extraction-failed`, `promote-base-disagreement`,
> `promote-no-task-file`, `promote-task-file-untracked`, `promote-no-scope`,
> `promote-host-index-dirty` — and the host pre-flight tests the **index**
> only, never `status --porcelain`. Findings are reported all together except
> where one invalidates another. Every one of these has its measurement under
> `## Findings`.

Then, with no findings:

```
flock devteam/.run/locks/promote.lock  (L-2.4)
git -C <repo> fetch <meta>/commits.bundle HEAD:refs/devteam/sandbox/<id>
git -C <repo> cherry-pick --allow-empty --keep-redundant-commits \
    <base>..refs/devteam/sandbox/<id>
git -C <repo> update-ref -d refs/devteam/sandbox/<id>
```

On a conflict: `git cherry-pick --abort`, leave the ref for inspection, print
`promote-conflict` with the path list, exit 1. On success: write
`meta/promoted.json` — `{old hash: new hash}` in order, plus the host `HEAD`
before and after — and print one line per commit: `promoted <old> → <new>
<subject>`.

**`promote-uncommitted` refuses even when the commits are fine.** A worker
whose step ended with uncommitted work either died or did not finish, and
promoting the commits while discarding the remainder would make a partial
result look complete. The supervisor decides: re-dispatch, or `close --keep`
and read the patch.

**The guard must permit these commands** for the session running them: the
supervisor is host-side and `fetch` from a local bundle is currently in
`GIT_OUTWARD` in `guard.py`. Add a control to `test_guard.py`: `git fetch
<path ending .bundle> …` is index-class, `git fetch <anything else>` stays
outward. Cherry-pick is in `GIT_TREE`; it is judged as a write to the
repository, which the supervisor's session is permitted while it holds the
claim. Verify with the guard's control, not by reasoning.

## Findings

Recorded as they arrived, 2026-09-07. Ordered by what they change, not by when
they turned up. Every number below has the command that produced it beside it.

### The plan's own defects, measured before building to it

- **§3.1's command ORDER was wrong, and it silently changes what `status.txt`
  means.** It lists `git add -N . && git diff HEAD --binary` before
  `git status --porcelain -uall`. `add -N` stages intent-to-add, so every
  untracked path in the status that follows changes from `??` to ` A`.
  `MEASURED` on a throwaway repository, the same command either side of it:

  ```
  status BEFORE add -N        status AFTER add -N
   M tracked.txt               A loose.txt
  ?? loose.txt                 A newpkg/mod.py
  ?? newpkg/mod.py             M tracked.txt
  ```

  The `-N` cannot simply be dropped either: `MEASURED`, without it
  `git diff HEAD --binary` reports only `tracked.txt`'s change and omits
  `loose.txt` and `newpkg/mod.py` entirely, so the remainder patch would lose
  exactly the work L-2.1 exists to preserve. **status.txt is now taken first**,
  and `add -N` runs after it. This reaches further than tidiness: DESIGN §20's
  whole `-uall` discussion is about untracked-directory handling, and
  `check_scope`'s `foreign-write` classifies by `??`, so anything downstream
  would have silently stopped finding them. Handed over by 0.2.1's session,
  re-measured here.

- **`git bundle create <base>..HEAD` does not produce an absent file when
  `HEAD == base` — it fails.** §3.1 says "or absent if HEAD == base (record
  'no commits')". `MEASURED`: exit `128`, `fatal: Refusing to create empty
  bundle.`, and no file is written. Called unconditionally with a test for the
  file, every worker that committed nothing — the ordinary case — would have
  produced a `126` extraction failure. `rev-list --count <base>..HEAD` now
  decides whether the command is reached. Also handed over by 0.2.1, and
  confirmed here by the did-nothing case:
  `bundle skipped=no-commits (HEAD == base)`, no `extract-failed`.

- **§3.2's `promote-history-rewrite` condition is wrong in a way that fails
  open.** It says the finding fires when `base-is-ancestor.txt` is `1`.
  `MEASURED`: `git merge-base --is-ancestor` exits **128**, not 1, when the
  base is not a commit the repository has —
  `fatal: Not a valid commit name 000...` — which is neither "is an ancestor"
  nor "is not". A gate written as `== 1` reads 128 as no finding and promotes
  over a history it could not determine. The condition is now `!= 0`, and
  `promote-history-rewrite-undetermined` plants exactly that value. Found by
  running an extraction against a planted base, not by reading.

- **`promote-conflict` cannot be a gate finding, and `--dry-run` cannot report
  it.** The gate is pre-flight and stops before the apply; a cherry-pick
  conflict is only discoverable by cherry-picking. §3.2's table lists it beside
  six conditions that are all decidable from files. It is now a **runtime
  outcome** of the apply, and `--dry-run` says so in its own words —
  `conflicts are not determinable without applying; this dry run did not test
  for them` — rather than implying a clean apply it never attempted.

  **A dry-run conflict check does exist, was measured, and is declined.**
  `git merge-tree --write-tree HEAD <ref>` (git 2.43 here) exits 0 on a clean
  merge and 1 on a conflict, printing the conflicted stages, and leaves
  `git status --porcelain` empty with `HEAD` unmoved. It is declined because it
  performs a **merge** while the apply performs a sequence of per-commit
  three-way applies, and the two can disagree. A dry run that says "clean" and
  an apply that conflicts is worse than one that says "not determinable",
  because the first is believed. Recorded as considered rather than missed.

- **§3.2's "stopping at the first finding" contradicts every other check in the
  plugin.** `MEASURED` by counting append sites: `check_plugin` 20,
  `check_scope` 9, `check_trace` 29, `check_report` 15 — all print every
  finding. `guard.py` is a `PreToolUse` hook and so is binary by construction,
  which is not a precedent for a reporting tool. But the sentence's second half
  is a real rule about **cascades**, not about stopping: `check_plugin`
  registers a skill by its directory before parsing it precisely so one broken
  skill does not also emit a `missing-skill` for every agent preloading it.
  So `promote` reports every **independent** finding and suppresses the ones a
  fired finding has invalidated — if the history was rewritten below the base,
  the scope diff is being taken over commits that are not the ones which would
  be applied, and printing its verdict would bury the cause among its
  consequences. This is prose in §3.2's work section rather than a numbered
  decision, so it is corrected rather than superseded.

- **§3.2's host pre-flight, as it would naturally be written, refuses ordinary
  work.** `cherry-pick` refuses on a dirty **index**, not a dirty worktree.
  `MEASURED`, four ways:

  | Host state | cherry-pick |
  |---|---|
  | staged change to an unrelated file | exit 128, `your local changes would be overwritten` |
  | unstaged change to an unrelated file | exit 0, applied |
  | an untracked file present | exit 0, applied |
  | unstaged change to a file the commit also touches | exit 128 |

  `git status --porcelain` is non-empty in the two cases that work, and per
  README §2 the manager and supervisors share one worktree host-side, so an
  unrelated unstaged edit is the **normal** state. A gate on `status
  --porcelain` would refuse real promotions routinely, and a gate that blocks
  legitimate work is one somebody switches off. `promote-host-index-dirty`
  therefore tests `git diff --cached --quiet` only; unstaged and untracked
  paths are **recorded** in `promoted.json` so a later conflict is diagnosable.
  The last row is path-dependent on what the bundle touches and belongs with
  `promote-conflict`, not in the pre-flight.

- **A task file that is not tracked declares no scope, and an empty scope read
  as permission is F-118 exactly.** `check_scope.load_tasks` enumerates with
  `git ls-files -z -- tasks/*.md`. `MEASURED` against the one real run: every
  task file there is tracked, and the mechanism that commits them is a worker
  appending its REPORT block (`skills/run/SKILL.md`), which happens *after* the
  work — nothing commits a task file at creation. So the window is real, and
  `promote` refuses rather than reading an empty scope as a grant. Split in two
  because the fixes differ: `promote-no-task-file` when the file is absent, and
  `promote-task-file-untracked` when it exists and git cannot see it — the
  second names the `git add` that fixes it, because a reader looking straight
  at the file will not otherwise work out why it is invisible.

### Found by running the thing

- **`git diff HEAD --binary` cannot represent a large file, and failing the
  extraction over it would refuse ordinary work.** `MEASURED` on a 2 GiB
  untracked file: `fatal: Out of memory, malloc failed (tried to allocate
  18446744071562723405 bytes)` — an overflow inside git's own binary-diff path,
  on a machine with 5.5 TB free and 157 GiB of RAM. It surfaced as a
  regression in an existing false-positive control,
  `fp-two-gibibytes-under-the-repo`, which asserts that a large write under the
  repository is allowed; the new extraction turned it into a `126`.

  A large uncommitted build artifact is **ordinary** — spec §4 records a
  sibling project whose compile peaked at 30.9 GiB — and the remainder is never
  promoted in any case, so the patch exists to be read. Files over 10 MiB are
  now named in `meta/uncommitted-oversize.txt` and excluded from the patch, and
  a patch git still cannot produce is recorded rather than made fatal.
  `status.txt` carries the list either way, which is why it is taken first and
  independently.

  **This changes the gate, not only the extraction.** `promote-uncommitted`
  reads `status.txt` **as well as** the patch: a remainder too large to diff
  leaves the patch empty, and a gate reading only the patch would promote the
  commits and call a partial result complete — the exact thing that finding
  exists to prevent. `promote-uncommitted-that-no-patch-can-represent` plants
  it.

- **Every backslash escape in `outer_script()`'s template is interpreted by
  Python before the shell sees it, and one of them became a NUL byte.**
  `outer_script()` returns an f-string. Written the obvious way, the name
  listing used `tr` with backslash-zero and backslash-n; Python turned the
  first into a real NUL in the generated script, and since a NUL cannot be
  passed in an argv string, `tr` received an empty set and translated nothing.
  The symptom was a step that ran, exited 0, and did nothing. `MEASURED`:
  `file(1)` reported the generated script as
  `POSIX shell script executable (binary data)`, and `grep` refused to print
  its lines. The pre-existing `printf '...'` formats survive the same treatment
  only by luck — Python turns theirs into a real newline inside single quotes,
  which the shell accepts as equivalent.

  **The comment written to explain this fell into it**, splitting across a real
  newline and leaving its remainder as a command the shell tried to execute
  (`a workers: not found`). So the rule is now enforced instead of documented:
  `run` refuses to execute a generated script that contains a NUL or fails
  `/bin/sh -n`, with a message naming the cause. A comment is advice; an exit
  code is not.

- **A stale hash citation passes `check_report` until a garbage collection, and
  then fails.** §3.4 asked whether promotion breaks the report check. For the
  `- HEAD <subject>` form it does not: `MEASURED`, `check_report.py` is
  `clean` on a task whose commits were promoted and whose hashes were rewritten
  `0e6dcaae -> be0aee9b`, because cherry-pick preserves subjects and the
  resolver matches on them. **That is the whole of §3.4 and it needs no fix.**

  The hash form is worse than L-2.2 says. A worker that cites a literal
  pre-promotion hash produces a citation which `check_report` accepts, because
  its test is `git cat-file -e <hash>` — existence, not membership. `MEASURED`
  on a promoted task whose hash was rewritten:

  ```
  cat-file -e says it exists?    YES
  is it in the branch history?   NO      (merge-base --is-ancestor)
  reachable from any ref?        0 ref(s)
  check_report.py                clean
  ```

  The object survives as a dangling object from the bundle fetch. After
  `git gc --prune=now`, the identical citation flips to
  `unknown-commit ... is not a commit in this repository`. So the verdict
  depends on whether an unrelated maintenance command has run — which is worse
  than either answer alone, and is the P-35b shape: the instrument answers
  "does this object exist?" when the question is "is this commit part of the
  history this report claims?".

  **Not fixed here, deliberately.** The fix is one line in `check_report`'s
  resolver — test ancestry rather than existence — but it changes the semantics
  of a shipped finding class, needs its own control, and has to be thought
  about against the legitimate `HEAD~1` form. 0.2.6 owns naming every finding
  class against its rule and is where it belongs; 0.2.4 owns putting L-2.2
  where the worker is standing. Widening in passing would put the change where
  nobody is looking for it, which is the reason 0.2.1 gave for declining the
  same shape.

- **The first live promotion proved less than it appeared to.** Promoting a
  single sandbox onto a host whose `HEAD` had not moved reported
  `promoted 8c211cc9 -> 8c211cc9` — the hashes are **unchanged**, because
  cherry-picking onto the base reproduces the same commits. The case passes
  without exercising the mechanism L-5 exists for. The width-two case is what
  distinguishes: two sandboxes from one base `df32a46`, disjoint scopes,
  promoted in order, `MEASURED` —

  ```
  promoted ad96287a -> ad96287a T-1: edit a
  promoted 16ad8d5c -> 16ad8d5c T-1: add b
  promoted 0e6dcaae -> be0aee9b T-2: edit other
  promoted f82e6da0 -> 3e7ee65e T-2: add a binary
  ```

  — the second pair rewritten, subjects intact, four commits on
  `git log --first-parent`. The control now **fails** if the second sandbox's
  hashes come back unchanged, because that means it did not test cherry-pick.

- **The binary-fidelity check failed on its own fixture rather than on the
  mechanism.** `printf '\x00\x01\x02BINARY\xff'` under the sandbox's `/bin/sh`
  wrote the 22 literal characters rather than 10 bytes, and comparing against
  the intended bytes reported `CORRUPTED` when nothing was. Replaced with a
  check that assumes nothing about what was written: 4096 bytes from
  `/dev/urandom`, `sha256sum` taken **inside** the sandbox and printed on
  stdout, compared with the host's after promotion. `MEASURED` identical,
  `d04797a5…`, 14 NUL bytes in the file, and the file did not exist on the host
  beforehand — so the check could have failed.

- **Two defects in the control harness itself, both of which made one failure
  contagious.** A case that returned early skipped its `close`, leaving a
  sandbox behind; the next run then found two projects holding that id and
  refused — `sandbox: 'pro04' is ambiguous -- 2 projects have one` — so a single
  unrelated failure made every later run fail until `/tmp` was cleared by hand.
  Closing is now `try/finally`, and every sandbox call names its repository.
  The first failure it masked was a genuine one of my own: an apostrophe in a
  fixture's commit subject (`the neighbour's file`) inside a single-quoted
  shell string, reported as `sh: 1: Syntax error: Unterminated`.

### The live proof (§4)

On a throwaway repository outside this tree, with `T-1` declaring `Scope. src/`
and a `neighbour/` directory it does not own. Paths elided; every line is
copied from the run.

```
### (a) a worker commits two files in scope and one outside it
$ sandbox.py open --repo <repo> --task T-1 --step S-1 --id live1
$ sandbox.py run live1 -- sh -c '... three commits ...'
$ cat <sandbox>/meta/commit-paths.txt
neighbour/other.txt
src/a.py
src/b.py
$ sandbox.py promote live1 --dry-run
promote-out-of-scope: 1 path(s) outside the declared scope ['src/']: neighbour/other.txt
promote live1: REFUSED -- 1 finding(s). Nothing was applied and nothing was written.
exit=1
$ git -C <repo> rev-parse --short HEAD
9bade3f          <- unmoved, and still one commit

### (b) the same scenario without the out-of-scope commit
$ sandbox.py promote live2 --dry-run
promote live2: gate clean. Would cherry-pick 2 commit(s) onto 9bade3f:
  8c211cc9 T-1.S-1: update a
  99d3872c T-1.S-1: add b
  conflicts are not determinable without applying; this dry run did not test for them
$ sandbox.py promote live2
promoted 8c211cc9 -> 8c211cc9 T-1.S-1: update a
promoted 99d3872c -> 99d3872c T-1.S-1: add b
promote live2: 2 commit(s) applied; host 9bade3fa -> 99d3872c.
$ git -C <repo> log --oneline -3
99d3872 T-1.S-1: add b
8c211cc T-1.S-1: update a
9bade3f base
$ git -C <repo> for-each-ref refs/devteam/ | wc -l
0                <- the sandbox ref cleaned up
```

**And the half that makes (b) mean something.** Those hashes did not change,
because the host `HEAD` had not moved. The width-two run above is where
cherry-pick is actually exercised, and the sibling repository beside every
promotion fixture is hashed before and after each case: unchanged throughout.

### The controls, and what breaking them proved

`python3 plugins/devteam/scripts/test_sandbox.py` → **51 cases, 23
false-positive controls (45%), green** in 23.8s. A control that cannot fail
proves nothing, so the gate was broken five ways and the suite re-run each
time. Each mutation was asserted to have applied before the run, because a
mutation that silently does not apply proves the opposite of what it looks
like.

| Mutation | What the control said |
|---|---|
| `promote-history-rewrite` gated on `== 1` instead of `!= 0` | `FAIL promote-history-rewrite-undetermined: expected promote-history-rewrite and the promotion SUCCEEDED` |
| the scope comparison replaced by an empty list | `FAIL promote-out-of-scope: expected promote-out-of-scope and the promotion SUCCEEDED` |
| `promote-uncommitted` reading the patch and not `status.txt` | `FAIL promote-uncommitted-that-no-patch-can-represent: expected promote-uncommitted and the promotion SUCCEEDED` |
| findings reported but not stopping the apply | **12 of 51 failed** |
| the host index pre-flight removed | `FAIL promote-host-index-dirty: expected promote-host-index-dirty, got: promote-conflict: cherry-pick stopped ...` |

**Two of those five are caught only by cases that did not exist when the suite
first went green.** They were added by asking, of each case already written,
what a mutation could break without any of them noticing — which is the
question that produced `promote-history-rewrite-undetermined` and
`promote-uncommitted-that-no-patch-can-represent`. Without them the first and
third mutations pass a green suite, because the cases that were there are
satisfied by the ordinary values (`1` and a representable remainder) rather
than by the boundary the gate actually has to hold.

**The last row is caught by a different finding than the one it removes**, and
that is the honest reading of what the pre-flight buys. With it gone the
cherry-pick still fails — on a conflict, naming no path, leaving the operator
to work out that somebody's staged work was the cause. The pre-flight does not
prevent breakage; it converts an opaque git failure into a named finding
carrying its own fix. That is worth having and is a smaller claim than
"it stops a bad promotion".

**A number in the fourth row was wrong for ten minutes and is corrected here**:
the run that produced it was piped through `head -8`, which cut the summary
line off, so it read as 8 failures. Re-run without the pipe: 12. The reporting
command, not the mutation, was the instrument that lied — which is the same
class as everything else in this list and the reason every figure above names
the command beside it.

The scope gate was additionally removed at the call site on a live fixture,
rather than in the suite, to answer "what else could make this pass?" — with
the gate present the out-of-scope commit is refused and `neighbour/other.txt`
stays `theirs`; with `covers_declared` forced to return True the same commit
lands and the file becomes `mine`. And the guard's new case was mutated the
same way: with the bundle branch removed,
`FAIL fp-git-fetch-from-a-local-bundle-is-index-class: REFUSED, expected to
allow`.
