## 2. Decisions

### Reversed

- **L-9.1 — `the target is the fixture, through iterate` — REVERSED
  2026-09-07 by L-9.6.** Its reasoning was *"the mechanism has never run; the
  state exists"*, and the second clause was false in the way that mattered:
  the state exists but nobody owns it. Recorded rather than deleted, because
  the argument it made — that a new target spends the interview and the plan
  again before any 0.2 mechanism is reached — **is still true and is the price

- **L-9.5 — `fixture defects are fixed only where fixing them exercises a
  pipeline mechanism` — RETIRED**, having no subject once the fixture is not

### Settled by the owner, 2026-09-07

- **L-9.6 — the target is a new, small, real project of the owner's, built
  from nothing.** *Why:* the run measures mechanisms that require a client —
  the interview, the charter amendment a client signs, finding disposition,
  P-27's window — and a client who did not commission the work cannot supply
  them. A briefed session standing in for him produces a number for every
  measurement while answering *"can the pipeline execute its procedure against
  a synthetic principal?"*, which is not the question. *Declined:* the
  fixture (no principal); a sibling repository (own lock regime, other
  sessions live in them).
- **L-9.7 — the run is TWO cycles on that project: cycle 1 builds it, the
  owner uses it, cycle 2 iterates.** *Why:* `iterate` runs only on a finished
  cycle, and firing `iterate` is the single thing this subcycle exists for. A
  new project is otherwise another cycle 1 and leaves the mechanism unfired.
  *Cost, stated:* roughly double the scope L-9.1 assumed, which is why the
  ceiling below is revised rather than carried over.
- **L-9.8 — the project is a coin-price logger**, the owner's own idea and a
  precursor to a trading bot he wants: fetch the current price of a named
  coin, append it to a log, and report the percent change since that coin's
  previous record if one exists. **It cannot demonstrate its main feature on a
  single run**, so genuine repeated use between the two cycles is forced by
  the tool rather than requested of the owner — which is what makes cycle 2's
  first interview area answerable at all.
- **L-9.9 — the owner is the client, directly, and no session plays one.**
  *Why:* he is the principal now, which was the whole reason for L-9.6.
  *Consequence, stated rather than discovered:* 0.1 logged eighteen blocking
  stops in fifteen hours against an unusually available AI client, and a human
  client is the bottleneck the design has never actually met. That is a cost
  and it is also a measurement this run can finally take. **P-27 fires more
  honestly here than under the original L-9.2**, because a client who is
  asleep is genuinely late on a `REVERSIBLE` question rather than performing
  lateness to a brief.
- **L-9.12 — the escalation window is ONE HOUR, and it is a charter row the
  owner signs.** *Why:* P-27 has never fired, not once, and at any longer value
  §3.3's measurement of it returns zero — which would leave the mechanism this
  subcycle exists to exercise still unfired at the end of it. **Its review half
  has never had a single row to review either**, so a short window is also the
  only way to learn whether reviewing a night's worth at a checkpoint is
  tractable at all. *The trade, stated in the owner's terms before he chose:*
  a short window means he wakes to a "Decided without the client" table with a
  night of rows in it, on **his own project** rather than on a fixture where
  nothing was at stake for him. *Declined:* eight hours — nothing decided while
  he sleeps, but a multi-day run then idles through every night, which is
  HANDOFF §4's eighteen-blocking-stops bottleneck, and P-27 may never fire;
  three hours — fires on long gaps only, too few rows to learn whether review
  at volume works and still enough to surprise him.
  **What bounds the risk, and what that makes measurable:** only `REVERSIBLE`
  questions reach the window; `IRREVERSIBLE` and `CHARTER` always block
  regardless (`run` §537). So a short window is a bet that the pipeline's
  reversibility classification is correct — **and no question has ever timed
  out, so that classifier has never been tested.** The run therefore records
  *why* each question was classified `REVERSIBLE`, and the checkpoint reviews
  the **classification** and not only the decision. A question that should have
  blocked and did not is a finding about P-27's design, not about the answer.
  **This decision exists because a peer session read the revision and found the
  parameter missing** — L-9.2 carried the only value (*"one hour"*) and was
  deleted wholesale when L-9.9 made the owner the client, taking the value with
  it. Nothing in any check would have reported its absence.
- **L-9.10 — three requirements are settled before the interview, because
  each is a lesson this project has already paid for.** *(a)* The charter
  declares **one allowed external host**; HANDOFF §4 makes *"a worker observed
  contacting anything but the model API"* the trigger for unsharing the
  network, and a worker legitimately calling the price API would fire it. *(b)*
  Network-dependent tests are **split**: a structural half that always runs and
  a live half that skips loudly when the host does not resolve — 0.2.8's
  release gate went red one run in eight for exactly this. *(c)* The clock is
  **injectable**, because "change since the last record" is time-dependent and
  a deterministic test needs it.
- **L-9.11 — the charter carries a constraint that this cycle builds no order
  path, and adding one is an amendment.** *Why:* the owner excluded orders and
  the structure should refuse them rather than rely on anyone remembering. It
  is also the first constraint row this project has written for a reason
  outside the pipeline's own mechanics.
- **L-9.4 — width 2, then 3 only if the first two tasks promote cleanly.**
  Carried forward unchanged: the promotion lock and the base-moved path are
  exercised at width 2, and width 3 adds nothing new for a third of the budget.

### The ceiling, and the defect that made the old one unusable

- **L-9.3 — a budget ceiling is set, in the charter, and it is a stop.**
  Carried forward. **But its unit is corrected, and the correction is a
  finding.** L-9.3 originally read *"the estimate × 1.5"* while §3.3 checks
  the bill against *"the harness's measured tokens"*. Those are not the same
  unit. Every constant in the v3 model — `unit 440,000`, `r 0.78`,
  `overhead 150,000` — is fitted to cycle 0.1's task reports, and **cycle 0.1
  had no meter**: `find .internal/scratch -name budget.json` returns nothing,
  and `tasks/T-7.md:462` reads `budget: tokens~200000 minutes~20 (estimated;
  no exact token meter available to me)`. 0.2.8 measured the gap at **32× on
  one dispatch** (31,000 self-reported against 997,283 metered). As originally
  written the ceiling is breached during task one and §3.4's stop rule fires
  on an arithmetic error.
  **This is a plan predating its own instrument, not an oversight**: 0.2.9 was
  written 2026-09-05 and the meter arrived in 0.2.3, five subcycles and four
  days apart. The reconciliation could not have been written.
- **The ceiling, as the owner approved it:**
  - **Binding, and self-checkable from inside a session: dollars.**
    `scripts/session_cost.py` over the manager's own transcript **plus** the
    workers' spend summed across every sandbox's `meta/budget.json`. **Both
    numbers are named, or the workers' half is uncapped** — §8 records that a
    subcycle spends the quota twice and the two are metered differently.
  - **Reported, at every checkpoint: percent of a weekly window**, as summed
    per-reading movement with a reset counted as a **break**, never as an
    endpoint difference. §8: *"a correction recorded in tokens is one he
    cannot check."*
  - **Percent cannot be the binding unit.** `/usage` is a client built-in
    whose output never reaches the model, so a stop rule denominated in points
    cannot fire without waking the owner — across a multi-day run that is an
    escalation wearing a ceiling's clothes.
  - **The number, revised for L-9.7's two cycles: `$200`, `BLOCKED` at it.**
    The owner approved `$150` for the four-task single-cycle shape; two cycles
    on a project built from nothing is larger, and this is a change announced
    rather than an open question. Sized against §8's nine measured rows —
    `$10–15` for a subcycle that builds one mechanism, `$40` for one that
    rewires the pipeline, `$196.70` for all of cycle 0.2.
  - **Two window breaks are expected inside the run:** the reset on **Sep 9,
    7:59pm ET**, and the `+50%` boost expiring **Sep 13**. The last boost
    expiry arrived as a *complete quota reset* rather than a rescaling. **Ask
    which happened; never infer it from the display, which cannot show a

### 3.4 Stop rules

The run stops, with `BLOCKED` and a checkpoint, when any of these is true; the
plan says so in advance so that stopping is a decision already made and not a
judgement under sunk cost:

- the ceiling is reached (L-9.3)
- a host mutation outside promotion is measured — the property failed; stop and
  file it, nothing else matters more
- a `promote-conflict` at width 2 with disjoint scopes — P-12's guarantee
  failed somewhere; stop and file it
- the second `BLOCKED` on the same class in one task (P-20c's spirit applied to
  the experiment: the third attempt belongs to the owner)
- **the credential-refresh risk from 0.2.3 §3.2 materialises** — a worker
  cannot authenticate mid-run. Stop, record exactly what was observed. It has
  survived every run so far because none lasted long enough; L-9.7's two
  cycles across two window breaks are the longest exposure it has ever had.

GATE 4 as the checkpoint skill says, with its five rules. Then this file's

reasoning** — the plan written to validate the pipeline turned out to have no
client, found before the budget was spent rather than after.
