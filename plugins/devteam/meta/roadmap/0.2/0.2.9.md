- **L-9.13 — the keepalive tick is `/loop /devteam:run tick` at TWENTY
  MINUTES, and the number belongs in the charter beside L-9.12 rather than in
  whoever types the command.** *Why the mechanism:* `run` §9 already defines
  `tick` as one pass of §4 and stop, and names `/loop` as its driver — nothing

  background and **the harness wakes the manager when a worker reports**, so
  ticks buy nothing while work is in flight except a fallback against a
  dispatch that hangs without notifying. The tick is load-bearing in exactly
  one phase — **nothing running, blocked on the client, client asleep** — where
  no wake is coming and the tick is the only thing that can notice L-9.12's
  window expired and proceed on the recommendation. That is precisely the phase
  L-9.12 exists to exercise.
  **THE CONSTRAINT THAT SETS THE NUMBER, AND IT IS A FINDING RATHER THAN A
  PREFERENCE: a tick interval at or above the escalation window silently
  BECOMES the window.** With hourly ticks a question timing out at T+1h may not
  be acted on until T+2h — the charter says one hour, the run behaves like two,
  and nothing anywhere reports the discrepancy. The effective window would be
  set by an operational parameter the charter does not carry, which is the same
  defect shape that lost L-9.2's window value entirely. **So it is written here
  and signed with the charter, not passed as a habit.**
  Twenty minutes gives a worst case of 1h20m against a 1h window and an average
  of 1h10m — a ~17% overshoot that does not change the character of what the
  owner chose — at roughly 27 ticks across a nine-hour night, each skipping §1
  by §9's instruction. *Declined:* five minutes, which buys fifteen minutes of
  accuracy against a window that is itself an approximation, for three times
  the empty passes; and varying the interval by phase, which is correct in
  principle and adds a mechanism a tired operator gets wrong at 2am — one
  number that is always safe beats two that need judgement.
  **THE MACHINE DOES NOT SUSPEND, AND THE SCARE THAT SAID OTHERWISE IS
  RECORDED HERE BECAUSE ITS SHAPE MATTERS MORE THAN ITS ANSWER.** `MEASURED`

```
gsettings get org.cinnamon.settings-daemon.plugins.power sleep-inactive-ac-timeout
                                                   -> 0       (0 means NEVER)
gsettings get org.cinnamon.desktop.session idle-delay
```

  **What went wrong, and it is this cycle's own failure shape at one remove.**
  An earlier draft of this decision carried an alarm: `sleep-inactive-ac-type

### 3.4 Stop rules

The run stops, with `BLOCKED` and a checkpoint, when any of these is true; the
plan says so in advance so that stopping is a decision already made and not a
judgement under sunk cost:

- the ceiling is reached (L-9.3)
- a host mutation outside promotion is measured — the property failed; stop and
  file it, nothing else matters more
- a `promote-conflict` at width 2 with disjoint scopes — P-12's guarantee
  failed somewhere; stop and file it
- the second `BLOCKED` on the same class in one task (P-20c's spirit applied to
  the experiment: the third attempt belongs to the owner)
- **the credential-refresh risk from 0.2.3 §3.2 materialises** — a worker
  cannot authenticate mid-run. Stop, record exactly what was observed. It has
  survived every run so far because none lasted long enough; L-9.7's two
  cycles across two window breaks are the longest exposure it has ever had.

#### THE FINDING THAT MATTERS MOST: promotion is unsafe at width above one

**Four instances across two tasks, on three different files, none of which the
blocked step had touched.** A sandbox's overlay lowerdir is the **live host
repository**, so any concurrent uncommitted edit at any moment during that
sandbox's run is copied permanently into its upper layer — and pins
`promote-uncommitted` there **even after the other party commits**. Re-running
the same sandbox does not clear it; the interference is baked into the overlay,
not a live re-checkable fact.

The three triggers measured: a `.pyc` left by a verifier's own sanctioned
host-side `pytest` run; a sibling task's in-progress task-file bookkeeping; and
**the manager's own uncommitted record**. That last one is the sharp end — the
manager is the party most often holding an uncommitted edit, and it is also the
party that cannot be excluded.

**A recovery route now exists and is proven three times**: open a fresh sandbox
at current host HEAD, carry the already-built commit in through the sandbox's own
unpoliced `HOME`, and cherry-pick it there so it promotes through the real gate
with base-ancestry and scope-diffing running in full. Nothing already verified is
re-spent. **But it is a workaround a supervisor must already know to reach for,
not a property of the tool**, and two supervisors independently had to discover
it.

**The repair named by the supervisor who hit it twice:** `promote` should
re-derive its uncommitted-remainder check **fresh at promote time** rather than
trusting a snapshot frozen at the sandbox's exit, which can go stale between then
and the decision to promote. **This is the finding to fix before any run at width
above one is attempted again.**

### `check_refs` cannot tell a cited path that is tracked from one that merely exists

**Measured immediately after, on the same project.** `git commit -F msg --
devteam/research/` exited 0 and committed `CURRENCY.md` while silently omitting
the new digest beside it: **a pathspec commit takes tracked files only, and an
untracked file named by the pathspec is not an error.** The commit that
introduced `D-2` and `R-5` — both of which cite that digest by path — therefore
shipped two dangling citations in authority documents.

**CORRECTED 2026-09-10, and the correction is the finding.** This entry first
said `check_refs` stayed clean because it *"resolves references against the
working tree"*. **That is false.** `check_refs` reads git-tracked files, exactly
as `check_trace` does, and it has a `broken-link` class that resolves markdown
links against them. The real mechanism is narrower and more useful: **the
citation was written in backticks rather than as a markdown link**, so
`broken-link` never applied to it. A path in backticks is prose; the same path
written in markdown link syntax — square brackets followed by parentheses — is a
checked reference. **The citation's FORM silently decides whether it is
verified**, and prose documents reach for backticks by default.

*(Noted in passing, because it cost a commit here: `broken-link` does not
respect code spans. Writing that contrast with a literal example made the
checker read the example as a real link and report it. A check that cannot be
written about in the repository it guards is a small instance of the same
family.)*

So the gap is not "no check asks whether a path is tracked" — one does, for
links. It is that a path can be cited in a way that opts out of the check
without anyone choosing to.

**It is N-6's family on a git primitive rather than on a check** — the invocation
implies a directory, the exit code says success, and the omission is invisible
from both. Worth recording because the failure mode is a repository that is
self-consistent for whoever wrote it and broken for everyone who clones it.
