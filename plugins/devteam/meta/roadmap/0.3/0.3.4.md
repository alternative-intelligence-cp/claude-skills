- **L-4.1 — one command, `scripts/manager.py`, holds the acts; each verb
  checks its preconditions, refuses rather than proceeding, and commits
  through the gate.** (theme 3; L-5) *Settled by:* planning, open to the
  owner's overruling.
  - **The verbs:** `lock`, `claim`, `dispatch`, `dispatched`, `land`,
    `close`, `stop`, `reclaim` and `accept`. The row's **commit** is
    `gate.py commit`, which learns three things (L-4.8).
  - **One home for the board-writing grammar** (P-34). Every value a verb
    writes is generated from the thing it restates, never typed (F-26).
  - **A refusal** exits 1, names the precondition that failed, and says what
    to do. A verb that cannot run exits 2, as the result contract says. Each
    refusal class names a rule in CHECKS.md, and `check_plugin`'s `EMITTERS`
    reads `manager.py`.
  - **A verb that writes `devteam/` refuses unless the session running it
    holds the writer lock.** That means its `CLAUDE_CODE_SESSION_ID` is on the
    board's `**Writer.**` line; the variable is set in a session's Bash
    (`MEASURED`). *Why:* `guard.py` judges command text, and it sees no write
    target in `python3 <script>`. It reads the lock for edits only
    (`lock_state`, `guard.py`:456–462). So a command that checked nothing
    would be the way around P-13.
  - **It commits through a function the gate exposes.** That function is
    landed first, as its own commit with no behaviour changed, as 0.3.3's
    §3.4 moved the block parse. *Why not a subprocess:* the refusals and
    what stands come back as data, which the verb reports whole.
  - *Declined:*
    - *a script per act* — as many homes for the board grammar and the lock
      precondition as there are acts;
    - *more precise prose in the skills* — L-5's own declined alternative,
      measured failing.
- **L-4.2 — a stop releases its claim, and a restart is a new claim.**
  (F-130, F-39; P-28) *Settled by:* owner, 2026-09-25 14:29:51 EDT, choosing
  *"Release it (Recommended)"* over *"Keep it, uncounted"* and *"Keep it,
  counted"*. It amends the cycle README's 0.3.4 row in one respect: *"counts
  in-flight and stopped rows against width"*.
  - **What it means.** `stop` removes the task's in-flight row in the stop
    commit, and the task's board row reads `BLOCKED on …`. `reclaim` claims
    it again under a new label, checked for scope, dependencies and width like
    any claim. Width counts the in-flight rows, and each one is a live claim.
    P-28 stands: a stop stops its own task and nothing else.
  - *Why:* the row's words and P-28 cannot both hold at width 1.
    - A stopped task already holds no scope (`MEASURED`). `check_scope` reads
      a claim as live only under a `RUNNING` title (`check_scope.py`:239).
      The corpus's manager wrote at RECORD.md:1683: *"T-16's title reads
      `NEEDS-DECISION`, so it holds no scope"*.
    - That manager released T-16's row this way, inside T-19's claim commit
      `626f428`, 5 h 15 min after T-16's stop commit `3da82d8`
      (RECORD.md:1629, 1683). T-16 was `BLOCKED on T-19`. So a stopped row
      that kept the only width slot would have deadlocked the corpus
      (`REASONED` from those two states).
    - No committed board ever held more in-flight rows than its width,
      because the manager released T-16's row in the very commit that claimed
      T-19 (`corpus_width.out`).
    - F-130's own remedy named both shapes: *"a stopped task's row either
      leaves the table at its stop or is counted by a written rule"*
      (RECORD.md:1630).

  *Declined:*
  - *keep it, uncounted* — a scope reservation today's checks do not make, two
    kinds of in-flight row, and a stopped-claim row in the recovery table;
  - *keep it, counted* — P-28 superseded, and the corpus deadlocked.
- **L-4.3 — the title follows the board: only the manager's commands write a
  task's title, each in the commit that moves its board row.** (F-19, F-78,
  F-90, F-98, F-107; P-27b) *Settled by:* owner, 2026-09-25 14:29:51 EDT,
  choosing *"Manager writes every title (Recommended)"* over *"Closing title
  only"*.
  - **Who writes what.**
    - `claim` and `reclaim` write `RUNNING (since <date>, <label>)`.
    - `stop` writes the stop from the stopping block: `NEEDS-DECISION
      (<what>)` for a `NEEDS-DECISION` block, and `BLOCKED (<why>)` for a
      `BLOCKED` or `RED` one. The parenthetical names what the board row
      names — the questions, or the task — so the two cannot differ.
    - `close` writes `DONE (<date>)` or `ACCEPTED (<date>, D-n)`.
    - The supervisor writes no title. Its status is its REPORT block's
      `status:`, which it lands before it reports; that block is its record of
      having stopped.
  - **P-27b is superseded in that respect** (L-4.14). The role that can stop
    still owns the record of having stopped — its block, with every question
    and open item as lines (L-3.4). The title is the manager's echo of the
    board.
  - *Why* (`MEASURED`, `corpus_close_windows.out`):
    - At none of the corpus's 17 closes did the title, the board row and the
      requirement move in one commit. The supervisor's last closing title came
      1 to 7 commits and 7 to 91 minutes before the manager's advance, and
      3,200 minutes before it for T-17, across the weekly-quota stop.
    - Five tasks — T-4, T-7, T-9, T-14 and T-15 — had a closing title reopened
      before they closed. `check_scope` reads a claim as live only under a
      `RUNNING` title (`check_scope.py`:239), so while each read `DONE` its
      scope was judged by nothing. That is F-98's mechanism.
    - T-12 ran the other way. Its row read `DONE` at `74e8d62`, and its title
      read `NEEDS-DECISION` for 91 commits and 4,237 minutes, until the
      manager corrected it at `ffcca83` (F-107). That is the correction
      `supervise` §7 says a manager cannot make.
    - The corpus wrote 33 distinct `RUNNING` titles. Six fall outside the
      claim's grammar, and all six carry a restart's reason after the label

- **L-4.5 — a finding a subordinate's commit adds is accepted by a decision
  made first, tied to the claim.** (0.3.2 §3.4, §3.7) *Settled by:* owner,
  2026-09-25 14:30:24 EDT, choosing *"Yes, decided first, tied to the claim
  (Recommended)"* over *"Never"* and *"Yes, the client only"*.
  - **The form.** An `Accepts.` item may end `(until T-n)`.
    - While T-n's board row reads `CLAIMED`, the item accepts its finding in
      any commit that adds it. It is not stale while the finding does not
      fire.
    - From the commit that moves T-n's row off `CLAIMED`, it accepts nothing.
      A finding it accepted that still fires is refused unless that commit
      decides it again.
    - The item itself falls due in that commit, which supersedes the decision
      (P-23). That is the ledger's `open (until T-n)` trigger (L-3.12).
  - **Who decides stays P-51's**: the class. The manager decides a
    `REVERSIBLE` acceptance, with L-4.6's question; the client decides a
    `CHARTER` one.
  - **The same form serves a fix.** Today a supervisor whose commit fixes an
    accepted finding makes the acceptance stale. The gate refuses that commit,
    and only the manager can supersede the decision (0.3.2 §3.7's general
    form). The remedy is for the manager to tie that acceptance to the claim
    first. If it did not, the supervisor stops on the refusal, and the manager
    supersedes the acceptance with the `(until T-n)` form and claims the task
    again.
  - **A supervisor that meets a refusal it cannot fix** stops `BLOCKED`,
    naming the finding as the gate printed it. The manager decides and runs
    `accept`, and the next claim's commit lands.
  - *Why:* 0.3.2 §3.4 found (`MEASURED`) that no decision can accept a
    refusal a supervisor's own commit adds. *Never* would let a check that
    misfires on a task's own output block that task until a plugin release.
    The client's terminal, which runs no hook, would then be the only way
    through. The corpus never carried an `Accepts.` field
    (`git log -S'Accepts.'`: 0 commits).

  *Declined:* *never*; *the client only*.

## 3. The work

Seven steps. Each is committed on its own, with `run_controls` green and
`check_plugin` clean, so that a rotation can fall between any two. In each:

- the planted case comes out as expected before the real result is believed
  (P-35b);
- every new assertion is shown to fail on a mutant of a copy of the whole
  plugin (`mutants.py`);
- every verb's refusal is planted before its success, and each class both
  ways;
- the commit body names the register rows it closes (the cycle README's §9);
- the documents are brought level for what the step changes — CHECKS.md's
  rows, FORMATS, the templates, and the skill text that describes it. A class
  with no CHECKS.md row fails the plugin (`unruled-finding`), and a skill that
  describes the old act by hand is a second home, now wrong (P-34);
- every example the step adds or changes in a document is executed as
  written in a scratch project, in `.internal/scratch/0.3.4/examples_3_n.py`,
  with its output kept beside it — the owner's rule.
