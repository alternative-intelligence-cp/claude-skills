## 2. Decisions (settled — see [`README.md`](README.md) §6)

L-5, L-6, L-9 and L-18 bind; do not re-litigate them here. Local to this
subcycle:

- **L-1.1 — four results, four exit codes, one line.** Every check ends in
  exactly one of:

  | Result | Exit | Means |
  |---|---|---|
  | `clean` | 0 | everything the check owns was evaluated against everything it exists to read, and nothing was found |
  | `findings` | 1 | at least one finding |
  | `could not run` | 2 | unchanged: the check could not start — its arguments, no repository, no `devteam/` |
  | `not evaluated` | 3 | no finding, and at least one part the check did not evaluate, each named with its reason |

  - A run with findings *and* parts not evaluated exits 1, and its line names
    both.
  - Every result line carries its denominators — what was read, and how many
    rows of each kind — and names every part not evaluated.
  - Every check takes `--json`, with one schema for all of them, and the gate
    reads that. The line is rendered from the same object, so the two cannot
    disagree.

  **Why 3 and not 2** (L-6 leaves this choice here). Exit 2 means the tool
  cannot answer, and the remedy is in the invocation. Exit 3 means the tool
  answered about the project and names what it could not read, and the remedy
  is in the project. One code for two remedies sends one of them to the wrong
  place. In 0.2.6, `unreadable` and `not-utf8` were moved to exit 2
  (`docs/CHECKS.md`, *Withdrawals*). Each is a project file the check could
  not read, which is the project's state, so both move to 3.

  **Why 1 over 3 when both hold.** A finding is definite, and the line also
  names the parts not looked at, so nobody reads a partial finding set as the
  whole.

  *Declined:* sharing exit 2 with *could not run*; and letting
  `not evaluated` outrank findings.
- **L-1.2 — excluded is not the same as not evaluated.** A class can be
  excluded by a declaration: a flag the caller passed (`--pre-plan`), or a
  project declaration the check reads itself (the charter's
  `Containment: guard-only`, under which there is no harness meter). An
  excluded class is named in the result line and does not change the exit
  code. Anything else the check did not evaluate is `not evaluated`.

  *Why:* onboarding's gate must still be able to exit 0 with `--pre-plan`.
  And FORMATS' *"an absent measurement is not a finding"* stays true without
  reading as clean. The difference is who said so. An exclusion has a
  declaration behind it that a reader can check; a gap has none.

  F-32's T-4 case is a gap, so it is `not evaluated`. The comparator was
  missing on a `structural` project because the sandboxes had been closed
  (RECORD.md:356), and no declaration says it should be.
- **L-1.3 — zero rows from a non-empty source is `not evaluated`, and so is a
  partial read.** Each parse site counts two things: the rows its source
  offers, by a loose shape (a table line, a list item, a field line), and the
  rows its grammar accepts.
  - Rows offered that do not parse make the site `not evaluated`, and each
    unparsed row is named by file and line.
  - A source that is genuinely empty is `clean`, with its zero shown in the
    denominators.
  - A field whose value continues past its first physical line, where the
    check reads only the first line, is `not evaluated`, naming the field.
    This is the cycle README's §9 wrapped-field case.

  Reading continuation lines is 0.3.2's work, with F-132. 0.3.1 makes each gap
  visible and fixes no individual parse.
- **L-1.4 — the checks read untracked files, and report each one.** Every
  check that enumerates `devteam/` reads untracked, non-ignored files as well
  as tracked ones. Each untracked file is reported as a finding of its own
  class. This is F-131's first remedy, which the register chose *"because it
  turns the miss into a finding rather than a step someone must remember"*.
  Ignored files, `devteam/.run/` among them, stay invisible.
- **L-1.5 — the gate checks the commit it is about to make, before it
  exists.** `gate.py commit` takes a message and named paths, then:
  1. builds the candidate commit, without moving any ref: HEAD's tree with
     those paths' working-tree content, HEAD as parent, and the message given;
  2. evaluates every tree- and history-derived class in a temporary worktree
     at the candidate, and the same at HEAD;
  3. commits **only if the candidate adds no finding and no part not
     evaluated** beyond HEAD's, net of accepted findings (L-1.6) and the one
     allowance below;
  4. commits the named paths, and checks that the commit it made has the
     candidate's tree and the old HEAD as its parent. It refuses if HEAD moved
     in between. This is the lock-commit guard that held from the ninth move
     on (register, *What worked*; RECORD.md:1379).

  Working-state classes — `foreign-write`, `dirty-tree` and the new
  untracked-file class — are read from the live checkout and printed. Of
  those, only an untracked file under `devteam/` that the commit does not
  name refuses the commit, as the run's gate did (RECORD.md:432).

  The gate refuses on its own failures too: a check that exits 2, or output
  the gate cannot parse, counts as red (RECORD.md:430, 1139).

  - **Why the candidate.** It makes structural the property CONSOLIDATION §8b
    names: *the tree being committed was not the tree that had been checked*.
    It also evaluates F-114's history-derived checks against the history the
    commit will create, so that failure is refused before it lands instead of
    reported after. **This deviates from the map's wording, and is declared
    here.** The map says *"a post-commit re-run of history-derived checks
    (F-114)"*, which is the record's remedy (RECORD.md:1359–1360). Refusing
    before the commit catches the same finding one step earlier. If §3.5's
    planted cases show the candidate cannot be evaluated reliably, build the
    map's post-commit re-run instead, and record why under Findings.
  - **Why a ratchet** (F-12's scoping). A finding already present at HEAD does
    not refuse an unrelated commit, so a concurrent task's red file cannot
    block it (RECORD.md:99, :164). A commit that adds any finding anywhere is
    refused, even one whose finding lands in a file it did not touch — such as
    a declaration removed while another file still cites it. Every gate run
    prints the standing findings.

    *Declined:* requiring every check to be green project-wide, which
    deadlocked twice in the run; and scoping to the commit's own files, which
    misses exactly that removed declaration.
  - **The one allowance.** A `one-sided-link` does not refuse when its
    requirement reads `in-progress (T-n)` and T-n is in the board's in-flight
    table. That is F-19's window, keyed the way the run's gate keyed it after
    it failed closed twice (RECORD.md:486–487). It is the only permissive
    branch. Its control shows it refusing with the row removed and allowing
    with the row present. It is removed when 0.3.4's `close` makes the window
    impossible.
  - **Onboarding.** `gate.py commit --pre-plan` passes the flag to
    `check_trace`. The gate refuses the flag once the candidate holds any task
    file, so it cannot hide an uncovered requirement after planning.
- **L-1.6 — an accepted finding is a decision, classed like any other.**
  *Settled by:* owner, 2026-09-24, choosing *"A decision, classed as usual
  (Recommended)"* over *"You, every time"* and *"The manager, with a
  reason"*.
  - A decision carries an **`Accepts.`** field that names the findings it
    accepts, by check, class, anchor file and message.
  - The check reports those findings as accepted, names them in its line, and
    exits 0 when nothing else is found.
  - The decision's P-26 class decides who makes it. The manager decides
    `REVERSIBLE` acceptances alone, recorded as unreviewed under P-27. The
    client decides `CHARTER` ones.
  - An acceptance whose finding no longer fires is itself a finding
    (`stale-acceptance`), so the count returns to zero and stays a signal
    (CONSOLIDATION §8a).
  - An `Accepts.` line outside the grammar accepts nothing, and is reported.
  - Superseding the decision withdraws the acceptance (P-23).
  - A part not evaluated can be accepted the same way — for example, a check
    that stays blind until 0.3.2 fixes its parse.

  *Declined:*
  - *the client accepts every finding* — the strongest guard against quiet
    suppression, at the price of an answer for every acceptance;
  - *a baseline line with a reason and no decision behind it*, which is the
    *suppress it when the tree is annoying* reading that §8a warns about.
- **L-1.7 — a plugin hook refuses a direct commit.** *Settled by:* owner,
  2026-09-24, choosing *"Plugin hook refuses it (Recommended)"* over *"Git
  hook in each project"* and *"Gate command only"*. A small `PreToolUse`
  script beside `guard.py` refuses `git commit` in a devteam project from an
  agent session outside a sandbox, unless the commit runs through `gate.py`.
  The script sits beside `guard.py`, not inside it, as 0.2.10's `root_guard.py`
  does. The owner's own terminal is untouched. Workers in a sandbox are
  exempt, because promotion gates them (P-44).

  *Declined:*
  - *A git hook that `setup` installs in each project.* This is the record's
    own remedy (RECORD.md:1003). It also gates the owner's commits, is skipped
    by `--no-verify`, has to coexist with the project's own hooks, and has to
    find the plugin again after every plugin update.
  - *The gate command only*, with nothing refusing a direct commit until
    0.3.4 or 0.3.11. This is the form the run measured failing: six commits
    used the `git add -A` form that `run` §4.5 forbids by name (A1).
- **L-1.8 — 0.3.1 builds 0.3.4's `commit` primitive, and 0.3.2 and 0.3.3 keep
  their rows.** `gate.py commit` is 0.3.4's *commit named paths on a green
  gate*, so 0.3.4 adopts it instead of building a second one.

  So that nothing falls between subcycles, 0.3.1 does **not**:
  - fix any single parse — that is 0.3.2's: `board-drift`'s link rows (F-70,
    with F-107), F-132, F-34, F-37, F-88, and F-32's `~n`;
  - key a check to the claim window — also 0.3.2's (F-135, F-136);
  - build the ledger — 0.3.3's, which may absorb L-1.6's acceptances into its
    lines;
  - rewrite `run` and `resume` beyond sending their commits through the gate —
    0.3.4's.
- **L-1.9 — the rules.** Each new class names a rule in `docs/CHECKS.md`, or
  `unruled-finding` fails the plugin (0.2.6). Three rules are added, each
  numbered when it is written into PROTOCOL.md at the next free number:
  1. *a check never reports clean when it did not look* (L-6, written as a
     rule);
  2. *a commit to `devteam/` is checked before it is made* (L-1.5);
  3. *an accepted finding is a decision* (L-1.6).

  A rule these change is superseded by a new number, never edited (P-23).

## 3. The work

Seven steps. Each is committed on its own, with `run_controls` green and
`check_plugin` clean, so that a rotation can fall between any two. Each step's
planted case must come out as expected before its real result is believed
(P-35b).

### 3.1 The result contract in every check (L-1.1, L-1.2)

Write one shared module for the result object, the exit codes, the line and
`--json` — one home for all four (P-34). `check_trace`, `check_refs`,
`check_report`, `check_scope` and `check_plugin` all use it. No check changes
what it parses yet.

- `check_trace --pre-plan` becomes a named exclusion.
- `check_report`'s harness classes become named exclusions on a `guard-only`
  project. On a `structural` project whose `.sandbox` root or
  `meta/budget.json` is missing, they are `not evaluated` (F-32's T-4 case,
  RECORD.md:356).
- `unreadable` and `not-utf8` move from exit 2 to exit 3.
- `--blocking-only` stays a filter on the verdict, and still prints every
  advisory finding (CHECKS.md).

**The joint to watch.** `check_plugin`'s `unruled-finding` finds each check's
classes by parsing its source for bare `add(...)` and `findings.append((...))`
calls (CHECKS.md, *Why the class list here is machine-derived*). If the shared
module changes how a class is emitted, that parser must still find every one.
Otherwise it goes blind and still reports clean, which is the failure this
subcycle exists to end. Keep the emit form, or change the parser in the same
commit.

**Planted cases:**
- a check with one part not evaluated and no finding exits 3, and names the
  part;
- with a finding as well, it exits 1 and names both;
- `--json` and the line agree on the same run;
- `--pre-plan` exits 0, with the exclusion named in the line;
- a class emitted through the new path with no CHECKS.md row makes
  `unruled-finding` fire.

**Measure on the corpus:** record each check's line and exit on the
`pricelog` clone, before and after, under Findings.

### 3.2 Zero rows, partial reads and wrapped fields (L-1.3)

First, make an inventory of every parse site: the check, the source, the loose
shape, the strict grammar, and whether the source can legitimately be empty.
The inventory goes under Findings, because 0.3.2 works from it. Then apply
L-1.3 at every site.

**Planted cases**, one of each per check that parses rows. Each must refuse
to report clean:
- a non-empty source that parses to zero rows;
- one unparsed row among parsed ones;
- a wrapped field.

**False-positive cases**, which must stay clean:
- a genuinely empty source. A fresh `setup` project must still report clean,
  so `template-ships-a-finding` stays green (CHECKS.md);
- a multi-line list field that the check does read.

**Measure on the corpus:** every part that the `pricelog` clone now reports
as `not evaluated`, with its reason. `board-drift` is expected to be one of
them (F-70). **Fix none of them here** (L-1.8). Record each with the
subcycle that owns it. If no subcycle owns one, add it to the cycle README's
§5 row of the subcycle it belongs to, with the reason.

### 3.3 Untracked files (L-1.4)

Enumerate with `git ls-files --cached --others --exclude-standard`, and add
the untracked-file class.

**Planted case: F-131's own** (RECORD.md:1641–1642). `tasks/T-19.md` is
untracked while another file cites T-19. Its declaration is read, so there is
no `cited-undefined`, and the untracked-file class names the file. An

### 3.4 Accepted findings (L-1.6)

Build the `Accepts.` field on a decision in `DECISIONS.md`:
- its grammar, in FORMATS;
- its parse. An unparseable acceptance accepts nothing, because the run's
  parser failed closed (RECORD.md:430);
- matching, by the identity §3.5 also uses: check, class, anchor file and
  message, without line numbers;
- `stale-acceptance`.

**Planted cases**, on the `pricelog` clone, with its two findings accepted by
a decision:
- `check_trace` exits 0, and names both findings as accepted;
- a third finding makes it exit 1;
- an edit that shifts the anchors' line numbers does not un-accept them;
- an acceptance whose finding has been fixed reports `stale-acceptance`;
- an acceptance outside the grammar accepts nothing, and is reported.

### 3.5 The gate (L-1.5)

Build `scripts/gate.py` and its control. The gate reads the checks' `--json`,
never their text.

First, classify every class of the four project checks as tree-derived,
history-derived or working-state-derived, from what its code reads. The table
goes under Findings. It decides where each class is evaluated.

**Planted cases**, each one of the run's own failures where there is one:
- **F-114.** A commit that would give a requirement its third revision, which
  `re-litigated-requirement` counts over committed history
  (RECORD.md:1339–1340), is refused, and HEAD has not moved.
- **F-12.** A red finding at HEAD in a concurrent task's file lets an
  unrelated commit through. A commit that adds a finding in a file it did not
  touch, by removing a declaration another file cites, is refused.
- **§8b.** A defect in an uncommitted `devteam/` file that the commit does
  not name does not refuse the commit. The same defect in a named path does.
- **F-131 at the gate.** A commit of `BOARD.md` citing an untracked T-19 is
  refused, naming the file. With `tasks/T-19.md` named in the commit too, it
  goes through.
- **F-19's allowance, both ways.** With T-n in the in-flight table, the commit
  is allowed. With the row removed and nothing else changed, it is refused.
  This is the run's own mutation (RECORD.md:487).
- **F-24 and F-117.** A red result exits 1 with HEAD and the index untouched,
  and there is no second command left to chain.
- **Failing closed.** A check that exits 2 refuses, and so does `--json` the
  gate cannot parse.
- **HEAD moved** between the evaluation and the commit: refused.
- **The commit made is the commit checked.** Its tree equals the candidate's,
  and its parent is the old HEAD.

**The corpus, replayed.** In the clone, rebuild the candidates of real
`pricelog` commits — each commit's tree and message on its parent — and run
the gate on each. It must refuse the commits the record says went in over red:
the `check_refs` commit at RECORD.md:1001–1002, and the `one-sided-link`
window at RECORD.md:1112–1113. Record every refusal the record does not
explain as a false positive, and answer each before this step closes.

**If the candidate cannot be evaluated reliably**, build the map's post-commit
re-run instead (L-1.5), and record why.

### 3.6 Enforcement (L-1.7)

Build the hook script beside `guard.py`, register it in the plugin's
`hooks/hooks.json`, and give it a control. More than a third of the control's
cases must be false-positive controls, because *a guard that refuses
legitimate work gets disabled by whoever it obstructs* (P-35).

A direct `git commit` in a devteam project from outside a sandbox is refused.
All of these must pass:
- the same commit through `gate.py`;
- a commit in a repository with no `devteam/`;
- a worker inside a sandbox, with `DEVTEAM_SANDBOX` set;
- `git commit --help`;
- `git log`, `git status` and `git diff`.

**Then watch it act once, live.** A green control proves the script, never the
deployment (the check skill, *Before you trust a clean run*).
