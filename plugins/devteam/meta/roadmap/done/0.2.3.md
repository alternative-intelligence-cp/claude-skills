## 2. Decisions

L-2, L-4, L-6, L-7 apply. Local:

- **L-3.1 — a worker's identity inside is `DEVTEAM_PARENT_SESSION=<the
  board's writer id>`, set by the harness, and the guard treats a payload
  carrying it as the run's own agent.** *Why:* today a subagent inherits its
  parent's session id and the guard's scope rule keys on it; a headless
  process has a fresh id and would be refused its own task file (P-13).
  *Fails closed:* absent variable → `unknown`, never `theirs` — the exact
  defect that left the guard inert for a rehearsal (DESIGN §20) must not
  come back through this door. The guard's control gets both cases.
- **L-3.2 — the harness measures budget and model; the worker's own
  `budget:` and `model:` lines are cross-checked against it, not trusted.**
  *Why:* P-17c — today both are self-reported by the party least placed to
  know; the CLI's JSON result carries usage and the model actually used.
  A mismatch is a finding (`budget-mismatch`, `model-mismatch` in
  `check_report`), not a correction.
- **L-3.3 — the inside permission set is generated from the role's agent
  definition, one home, and passed with `--allowedTools`.** *Why:* a tool
  list in an agent file is the only enforced restriction the 0.1 design had
  (DESIGN §2 says so); making it the source of the headless allowlist keeps
  it enforced and keeps it single. *Declined:* a second list in
  `PERMISSIONS.md` (two homes; F-6, F-24, F-30 were all a grant and a rule
  disagreeing).
- **L-3.4 — read-only roles stay `Agent`-tool subagents and use `sandbox.py
  exec` for anything that must mutate.** *Why:* they cannot write anyway;
  the cost of headless (no `ListAgents`, no transcript) buys them nothing;
  and `exec` gives the verifier the mutable copy F-100 said it could not
  have. *Cost:* two dispatch mechanisms exist; the supervisor's skill says
  which role uses which, in one table.

### 3.3 The inside allowlist, generated

`sandbox.py allowlist --role <r>` prints the `--allowedTools` value derived
from `agents/<r>.md`'s `tools:` line, translated: `Bash` becomes
`Bash(*)` **minus** the outward set, which is the by-name list in
`templates/PERMISSIONS.md` §"Deliberately not requested" reduced to what
structure does not already make impossible — `Bash(git push:*)`,
`Bash(gh:*)`, `Bash(pip install:*)`, `Bash(uv add:*)`, `Bash(sudo:*)` — as
`--disallowedTools`. Everything filesystem-shaped is allowed (L-7).
`WebSearch`/`WebFetch` only for a role whose agent file lists them.

A control asserts the generated list for each of the three worker roles
against a golden file, and that changing an agent's `tools:` line changes
the output (the two-declared-lists test: agent file ↔ allowlist).

### 3.4 Dispatching from a supervisor, and the ten-minute wall

The supervisor's `Bash` call runs `sandbox.py dispatch … ` with
`run_in_background` (`../README.md` §4.5). 0.2.0 §3.4 measured whether the
backgrounded parent keeps the worker alive; build on what it observed:

> **Corrected as built: the branch is already decided and it is the first
> one.** 0.2.0 §3.4 measured both halves — a detached launcher AND the
> harness's own background shell as the direct parent — and both survived
> `sleep 720`/`sleep 660` past the ten-minute foreground limit. So
> `--die-with-parent` is the whole reaper and **nothing below is built**: no
> `setsid`, no double fork, no pidfile of its own, no reaper. `dispatch`
> writes `meta/pid` through `run`, as `run` already did.

- if it survives: `dispatch` writes `meta/pid`, and the supervisor is
  re-invoked by the harness when the process exits; it then reads
  `meta/report.txt`
- if it does not: `dispatch` double-forks a detached process with its own
  session (`setsid`), writes `meta/pid`, and the supervisor polls
  `sandbox.py status <id>` at an interval it states in the heartbeat; the
  `--die-with-parent` semantics then bind the worker to the detached
  reaper, whose own death kills the worker — record this in `status`'s
  output so recovery can see it

Either way the heartbeat (`devteam/.run/locks/<TASK>.heartbeat`) gains the
sandbox id: `waiting on S-n (<role>, dispatched <time>, sandbox <id>)`.

```

```

> **Corrected as built: the line carries `root <abs>`.** §3.6 requires
> `check_report` to find `meta/budget.json` "from the `.sandbox` file", and
> the format as planned carries only the sandbox **id**. Resolving an id to a
> directory means resolving `DEVTEAM_SANDBOX_ROOT` the same way the writer
> did — a machine-local environment variable, and a second home for a path.
> The writer states the path instead.

`run` §3's recovery table (0.2.4) reads it after `ListAgents`, the heartbeat

worker, so every `.sandbox` line reads `exited` or names a dead pid — that
is P-14's "every claim is stale after a restart", now with a reason a
reader can see.

### 3.6 `check_report.py`: `budget-mismatch`, `model-mismatch`

When `meta/budget.json` exists for a step (the sandbox root is findable
from the `.sandbox` file), compare the REPORT's `budget:` and `model:`
against it. Tokens within 10 % or minutes within 20 % pass — the worker
cannot see the harness's exact counter; a `model:` that names a different
id fails. Controls for both, and the false-positive twin (a worker whose
figures match).

**Do not** make the check depend on the sandbox root being present: a
report from a `guard-only` project (0.2.4 §3.6) has no `budget.json`, and
the finding must then be silent, not `could not run`.

### L-3.1's premise, measured — and it is worse than the plan said

The payload above carries `session_id b6377e0d-…`, freshly minted by
`claude -p`, while the board's writer was the supervisor. The plan says the
worker "would be refused its own task file (P-13)", which is true. It is the
**other** half that matters more:

```
guard.py: if lock_state(writer, session) == "theirs": return None
```

A stranger's writes to the product tree are deliberately **not policed** — that
exit exists because two lock regimes over one tree turned a real team away. So
a worker judged on its own id is not merely refused its task file; its
out-of-scope writes go **unpoliced entirely**. That is DESIGN §20's inert
guard arriving through a new door, and it is why the fail-closed direction is
`unknown` and not `theirs`: `unknown` refuses `devteam/` **and keeps policing
scopes**.

The control that separates them is `sandbox-no-parent-still-polices-the-scope`.
A control that only checked `devteam/` passes under either reading — which is
the question worth asking of every case: not "does this pass?" but "what else
could make this pass?".

**The identity is borrowed, and the cost is stated rather than hidden**: any
process that can set both `DEVTEAM_SANDBOX` and `DEVTEAM_PARENT_SESSION` can
present itself as the run's own agent. On the host neither is ever set — both
come from the mount plan's environment allowlist, which is the whole of what
crosses `--clearenv`. That is defence in depth, not proof, and the code says so.

### A latent defect in `lock_state` that fails closed. Not fixed.

**A session id containing a `.` can never match the writer line.**
`lock_state` compares against `re.findall(r"[0-9A-Za-z_-]+", writer)`, an exact
token match added because `session in writer` once matched `"me"` inside
`"names"`. `.` is not in that class, so a dotted id tokenises into pieces and
never equals the whole. `MEASURED`, one session id, two writer lines, all else
identical:

```
writer=writer-session-0.2.3                  parent=SAME -> REFUSED
writer=b6377e0d-b921-49b6-90e0-36f2927cb31a  parent=SAME -> ALLOWED
```

Found because the first live dispatch's worker reported *"I cannot write to
the task file due to write protection"* and the fixture's writer id had dots
in it. Real session ids are UUIDs, so this does not bite today, and it fails
**closed** — a refusal, not a grant.

**Not fixed here, deliberately.** Widening the character class weakens the
substring protection that the exact-token match exists to provide, and that
protection has its own control and its own finding behind it. Trading one
guard rule for another in passing, in a subcycle about dispatch, would put the
change where nobody is looking for it. Recorded with its measurement so the
next reader has it.

### `declared_scope` told a reader to `git add` a file git already had

`promote --dry-run` on the first live sandbox reported
`promote-task-file-untracked` for a file `git ls-files` printed by name.
`MEASURED`:

```
git ls-files devteam/tasks/T-1.md   -> devteam/tasks/T-1.md
check_scope.load_tasks(...)         -> {} , unparsed []
sandbox.declared_scope(repo,'T-1')  -> ('untracked', [])
```

`load_tasks` enumerates tracked files **and** parses them, and a heading
without a status segment (`# T-1 — say hello`) is dropped silently — not into
`unparsed`, into nothing. `declared_scope` read the parser's silence as
evidence about the index. The fix line then names a `git add` that changes
nothing, and somebody following it concludes the gate is broken rather than
that their heading is.

Fixed by asking git directly instead of inferring, with a new finding
`promote-task-file-unparsed` naming the actual grammar. This is 0.2.2's code
and the shape it fixes is 0.2.2's own `promote-task-file-untracked` split —
the split was right and one branch was reached by a wrong test.

### The Google Drive control has no positive arm, and that shrinks a shipped claim

0.2.0 records *"a sandboxed worker connected to the owner's Google Drive,
successfully, in 11 milliseconds"*, and concludes that an unflagged worker
"could read or change" several hundred research documents. The connection half
reproduces exactly, `MEASURED` here with `--strict-mcp-config` absent:

```
Successfully connected (transport: claudeai-proxy) in 11ms
Connection established with capabilities: {"hasTools":true,...}
```

**But the tools never reach the model.** Two arms, identical but for the flag,
each asked only to name any Drive tool it had — an introspection question that
touches no document, chosen because the owner authorised *list only, no read,
no write*:

```
--strict-mcp-config off  -> 'NONE'   $0.0110   mcp-logs-claude-ai-Google-Drive/ created
--strict-mcp-config on   -> 'NONE'   $0.0055   no mcp-logs directory at all
```

An earlier pair asked for a file count and both returned `NO-DRIVE-TOOL`.

**So the flag-off arm cannot be made to succeed, and a control with no
positive arm proves nothing about the flag.** The honest reading: the connector
is started and authenticated, and its tools are not offered to a headless
`claude -p` worker on CLI `2.1.263`. 0.2.0's "could read or change them" was
inferred from the connection, not measured — the same P-35b shape as its own
`mcp-logs`-directory instrument, one level up.

**The flag is still passed, and the reason is restated smaller and true**: it
stops the CLI opening an authenticated channel to a document store nobody
asked it to open. Whether that channel's tools are exposed is CLI behaviour we
do not control and which a version bump can change; the flag does not depend
on it. What is **not** claimed any more is that it prevents a worker reading
the owner's Drive, because a worker reading the owner's Drive has never been
demonstrated. Nothing was read, modified or deleted in either arm.

### Found by running it

- **`--debug-file` drops a `latest` symlink beside its target, with an
  absolute path, and both poison the promotion.** `MEASURED`: with the log
  written inside the repository, `status.txt` listed
  `.devteam-dispatch-debug.log` and `latest`, `promote` refused with
  `promote-uncommitted`, and the extraction logged
  `cannot open <sandbox>/merged/latest: No such file` because the symlink's
  target is only real *inside* the namespace. **A debugging flag that changes
  the verdict is not a debugging flag**; the log now goes to the worker's HOME.

- **The CLI waits on stdin.** `Warning: no stdin data received in 3s,
  proceeding without it.` Three seconds is cheap; a backgrounded dispatch
  blocking on a stdin no supervisor will ever write is not, and it would look
  like a worker that hung. The command is now wrapped `exec "$@" < /dev/null`.

- **The harness's own liveness file lands in the worker's remainder.**
  `devteam/.run/locks/T-1.sandbox` is written host-side before the mount, so
  the merged view sees it as untracked. A scaffolded project gitignores
  `devteam/.run/` and the fixture did not; the second live run's `status.txt`
  listed **0 paths** once it did. Recorded because `dispatch` now depends on
  that gitignore entry, which is a written rule rather than a mechanism.

- **My own mutation runner left the tree mutated when it was interrupted.**
  It restored `sandbox.py` after each run on the happy path only. The run was
  stopped part-way — by an out-of-range `timeout` argument on the tool call,
  not by anything in the script — and left the hardcoded-allowlist mutation in
  place. `python3 sandbox.py allowlist --role verifier` returning the
  *implementer's* list is what showed it. This is 0.2.2's `try/finally` lesson
  about sandbox cleanup, in a new instrument, and **a mutation left applied
  looks exactly like a suite that passes**. The runner is `try/finally` now.

- **The control suite's own sandboxes lived outside the directory it cleans
  up.** `test_sandbox.py` builds a temp root and removes it in a `finally`,
  but sandboxes go to `sandbox_base()` — `/tmp/devteam-sandbox` — which that
  cleanup never touches. `MEASURED`: after the mutation runs, **seven** stale
  sandbox roots plus a `devteam-sandbox-control-*` tree were left in `/tmp`.
  0.2.2 made each case close its sandbox in a `try/finally`, which is what a
  *case* can do; it cannot help a case that dies in a way nobody anticipated,
  and a mutation run is exactly that. The suite now points
  `DEVTEAM_SANDBOX_ROOT` at its own temp root, so the existing cleanup removes
  them wholesale — **structure rather than discipline**, which matters here
  because the failure lands on the *next* run as
  `is ambiguous -- 2 projects have one`, a message about nothing being tested.

### The controls, and what breaking them proved

```
python3 plugins/devteam/scripts/test_sandbox.py       -> 65 cases, 26 false-positive (40%), green
python3 plugins/devteam/scripts/test_guard.py         -> 92 passed, 0 failed, 92 cases (47 fp, 51%)
python3 plugins/devteam/scripts/test_check_report.py  -> 39 passed, 0 failed, 39 cases (21 fp, 53%)
```

Every mutation below was asserted to have applied before its run, because a
mutation that silently does not apply proves the opposite of what it looks
like — and one of them was left applied by an interruption, which is the same
hazard from the other end.

| Mutation | What the controls said |
|---|---|
| `dispatch` branches on `subtype` instead of `is_error` | `FAIL dispatch-reads-is_error-not-subtype` |
| the allowlist is hardcoded rather than read from the agent file | `FAIL allowlist-follows-the-agent-file`, `FAIL allowlist-undefined-role-refuses` |
| `declared_scope` calls any unparsed file untracked again | `FAIL declared-scope-tracked-but-unparsed-is-not-untracked` |
| `dispatch` stops refusing a sandbox with no `--parent-session` | `FAIL dispatch-refuses-a-sandbox-with-no-parent-session` |
| the liveness line stops carrying `root` | `FAIL fp-dispatch-accepts-a-run-that-really-succeeded` |
| the guard falls back to the worker's own id (`theirs`, not `unknown`) | `FAIL sandbox-no-parent-still-polices-the-scope` — **this one case only** |
| the guard honours `DEVTEAM_PARENT_SESSION` outside a sandbox too | 6 failures, all of them pre-existing `fp-` cases about strangers |
| L-3.1 removed entirely | 3 failures |
| `check_report`'s model comparison dropped | `FAIL model-mismatch-when-the-worker-names-another-model` |
| the budget tolerances widened to 100× | `FAIL budget-mismatch-on-tokens`, `FAIL budget-mismatch-on-minutes` |
| an absent sandbox reported instead of silent | **32 of 39 failed** |

**One mutation is NOT caught and it is recorded rather than quietly dropped.**
Reading the REPORT's `budget:` field as `fields.get("budget")` — the list —
instead of joining it passes the whole suite. `str(['tokens=4210 minutes=9'])`
still contains `tokens=4210`, so the regex finds it either way. The joining
helper is load-bearing for `model:`, where a list crashed `.strip()` and the
crash is what found it; for `budget:` it is defensive only. Claiming the
control covers it would be the thing this cycle keeps catching.

**The dispatch controls need no model, no token and no money.** `dispatch`
resolves `claude` through `PATH` at `open` time and binds what it resolves to,
so a fixture script first on `PATH` exercises the real dispatch path with a
known result. That is how `is_error: true` beside `subtype: "success"` is
planted — the exact object 0.2.0 measured — without an unauthenticated account.
