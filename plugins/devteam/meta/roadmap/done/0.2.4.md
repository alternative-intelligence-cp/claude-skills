Written as dry-run → `promote` → `check_report` → verify, **and the consequence

host, and the remedy is a further commit, never a rewrite — which is what P-12b
required all along. The alternative, verifying an overlay, contradicts §3.2's

### The guard's third limit: measured, real, and unreachable in both places it runs

0.2.3's session had not looked at this and said so. `guard.py`'s docstring says
self-scoping uses `CLAUDE_PROJECT_DIR` *"because `cwd` follows the shell's `cd`
— and a `cd` into a protected tree, which is a read and allowed, would otherwise
disarm the guard for the next call."* Inside a sandbox `CLAUDE_PROJECT_DIR` is
not in the mount plan's environment map, which is closed by design.

**The protected-path rule is checked twice** — once from the project containing
the *target*, once from the project containing the *session* — and that is what
decides it. `MEASURED`, four arms, `CLAUDE_PROJECT_DIR` unset,
`DEVTEAM_SANDBOX` set:

```
target INSIDE the project (charter protects vendor/):
  cwd = the repo root      -> REFUSED
  cwd = a subdirectory     -> REFUSED
  cwd = outside the repo   -> REFUSED      the target-side check catches it

target OUTSIDE every project (a sibling repo — the only case the
session-side check exists for):
  cwd = the repo root      -> REFUSED
  cwd = outside the repo   -> ALLOWED      disarmed
```

So the disarm is real. Whether it is reachable:

- **On the host**, the harness sets `CLAUDE_PROJECT_DIR`, so `session_project`
  never follows `cd`.
- **Inside a sandbox**, taken from `build_mount_plan` — which is data for
  exactly this reason — rather than by attempting a write outside the
  repository, which this session must not do:

```
every writable entry in the plan:
  --tmpfs   /tmp
  --bind    <home> /home/devteam-worker
  --bind    <merged> <repo>
--remount-ro / : yes      --ro-bind entries: 6      total entries: 34
```

**Three writable things, none of them outside the repository**, so there is no
path left for the disarmed check to have been defending.

Written into KNOWN LIMITS with both measurements, both reasons it does not
bite, and **the entry condition that would make it bite** — a host session
running the hook without `CLAUDE_PROJECT_DIR`. Not fixed: adding the variable to
the environment map is also a change to the map's closed-set contract, which has
its own control, and the reachable half is already covered.

**The reachable half is controlled and the unreachable half deliberately is
not.** A control asserting the disarmed behaviour would lock a defect in place
rather than guard a property. What is controlled is that a protected path inside
the tree holds under all three `cwd`s — and the mutation proves which arm does
the work: removing the target-side check fails **only** the `cwd = outside` case,
so the other two were being carried by the session-side check all along.

### A template that ships a finding, and why only a scaffold can see it

The first was this session's own, added hours earlier: `F-100` is a real finding

They were invented to illustrate the `Status.` grammar. So the class is not *a
template citing this repository's identifiers* but **any bare identifier in an
installed template that survives the example strip and is not declared by the
scaffold** — and only the second kind is invisible to a reader who knows the
record perfectly, which is why it outlived the fix that found the first.

Neither is visible from inside this repository: `F-100` resolves here, and the
templates are not a project, so nothing had ever run a project's checks against
them. Both would have fired on **every project ever scaffolded**, from its first
check, forever.

**Mechanised, because the only instrument was a person deciding to look.**
`check_plugin` now scaffolds a throwaway with the real `setup.py` and runs the
client's own `check_refs` against it, requiring zero findings before any work is
done — `template-ships-a-finding`. It reuses the scaffolder rather than
reimplementing the install, so it cannot drift into passing on a project nobody
will ever have. Mutation-tested by restoring both original defects: each is
caught, by name.

The check is **gated on its inputs and the skip is printed**, because
`check_plugin`'s own control builds partial plugin trees with no `templates/`,
and reporting "scaffold failed" there would be the check answering a question
nobody asked — P-35b, inside a check written to catch a related shape.

### F-37 recurring, and the reason a hand-fix is not a fix

The end-to-end's first promotion was refused. `status.txt`:

withheld.* The manager fixed it by hand. **The fix never became a mechanism, so
it recurred on a fresh project a whole cycle later.**

**P-44 raises the cost from annoying to blocking.** A dirty tree used to fail a
precondition; an uncommitted remainder now *refuses the promotion*, so a
finished step does not land, for a file its own verification command created —
and the supervisor reads `promote-uncommitted` and goes to look at the worker.
Since this subcycle introduced the rule that upgrades the severity, it owns the

### Two of our own rules could not both hold, and a real supervisor found it

The end-to-end's whole point was to test whether a supervisor that had never
seen this pipeline could follow §3.2's sequence as written. It could — and it
found something better than a gap in the sequence.

Its work was correct: gate met (`1 passed`), scope clean, refs clean, and it
mutation-tested its own instrument. It still could not close:

```
supervise   a budget-mismatch is recorded, never corrected
verify      a non-zero check_report exit is a FAIL
supervise   a FAIL is re-dispatched once
```

and a re-dispatch cannot help, because the next worker cannot see the harness's
counter either. **Correct work, rejected permanently, over a finding nobody is
allowed to fix and nobody is able to fix.** Its own words: *"this is impossible
to satisfy."*

**It escalated rather than picking a rule to break**, which is exactly right and
is the only reason this is a fix rather than a mystery. A supervisor that had
quietly chosen one would have left no trace.

`check_report` now marks `budget-mismatch` `(advisory)` and takes
`--blocking-only`, which the verifier runs. **The flag changes the verdict and
never the report**: every advisory finding is still printed, and the verifier is
told to copy each into its verdict. A flag that hid a finding would be a way to
make one go away.

`model-mismatch` is deliberately **not** advisory. A report naming a model that
did not run is a report about a different run (P-40). That distinction is the
entire content of the flag, and the control case that proves it is the one that
would go green if the flag simply passed everything.

Both skills now carry the general rule, because the specific one will recur:
**if you cannot satisfy two of this pipeline's own rules at once, that is a
defect in the rules and an escalation — never a choice about which to break.**
This is DESIGN §20's rule-pair shape, instance eleven, and every one has been
found by a worker under time pressure, because a worker is the only party
required to satisfy every rule at the same moment.

### The cost instrument is retired, because this subcycle falsified it

Four subcycles have quoted a share-of-a-weekly-window derived from a dollar
anchor. **This one spent `$41.81` and the display did not move at all.** That is
the strongest single datum the table has produced, and it points the other way
from every number in it.

Read from the owner's `/usage`, and the gauge readings are from the committed
record rather than recollection:

```
87%  cycle start
88%  0.2.0   $12.23   104 requests
     0.2.1   $9.81     58
89%  0.2.2   $13.51    83
90%  0.2.3   $14.73   100
90%  0.2.4   $41.81   256     <- three times 0.2.3's spend, zero movement
```

Every method disagrees with the observation, and they do not disagree with each
other in a way that helps:

| Method | Predicts for 0.2.4 | Observed |
|---|---|---|
| chained from 0.2.0's `$12.23 = 1%` | `3.42%` | `0` |
| the aggregate — `$92.09` over five subcycles against a 3-tick move | `0.91–1.82%` | `0` |

**A prediction of three points against a movement of zero is not a rounding
error, and it cannot be repaired by widening the range.** 0.2.3 already recorded
that every percentage descends from a single integer tick and quoted a range
instead of a number; this reading says the problem is not precision but the
model.

### Why, from the owner — and the two halves are labelled differently on purpose

The anomaly was reported to the owner rather than smoothed into a plausible
number, and he supplied what no session can see from the inside. **He offered
the cause explicitly as a guess** — *"take it with a grain of salt as I'm just
guessing and it's had me confused for a while"* — so it is split here rather
than promoted whole.

**`MEASURED`, reported by the owner as fact:**

- He pays **$200 a month** on a subscription.
- *"If you just took my usage for the last week alone it would be well over
  $200 going by the usage output."*
- When his subscription quota has run out and he has fallen through to **API
  overage billing**, the `/usage` dollar figures *"seem to match up pretty
  well"* with what he was actually charged.
- **A 50% limit boost is active through September 13.** It has run **since
  May**, long before he held a subscription, and was extended from September 1.
  So it covered **every** reading in this table uniformly.
- **His quota has been reset unannounced, twice in the week this subcycle ran**
  — *"this week I have actually had three weeks worth of usage in one"*.

**`REASONED`, the owner's own hypothesis, and his words for it:** the dollar
column is **API-equivalent pricing**, which is why it reconciles with real
billing only during overage and not under the subscription.

**Two independent reasons the derivations could never have worked, and the
second is the one nobody had considered:**

1. **The numerator is in the wrong currency.** If the dollar figure is an
   API-list valuation and the gauge meters subscription quota, they are not
   convertible by any fixed ratio — the ratio would move with model mix and
   cache profile, which differ between every subcycle in the table.
2. **The numerator was zeroed mid-series, and the display cannot show that.**
   The quota was reset **twice during the week this subcycle ran** — the owner:
   *"this week I have actually had three weeks worth of usage in one."* A reset
   returns the gauge to zero, so **any two readings with a reset between them
   are not two points on one curve**, and nothing in the output marks where one
   happened.

   **This is the live trap for anyone summing the cycle**, and it is worth
   spelling out because the arithmetic looks so reasonable: the display read
   `88%` when this cycle began and `91%` after five subcycles, which invites
   *"five subcycles cost three points"*. **It did not.** Two full window refills
   sit inside that span, so the true consumption is three points **plus roughly
   two windows**, and a plan built on the three-point figure would underestimate
   what remains by something close to an order of magnitude.

**Corrected, in place, an hour after it was first written.** This section
originally gave the second reason as *"the denominator is not constant"*, citing
the boost. **That was wrong.** The boost has run since May and covered all five
readings uniformly, so it is a constant across the series and explains no
inconsistency within it. The instability is the **resets**, which are
irregular, unannounced, and invisible in the output. The mistake is left visible
rather than silently replaced (P-23's spirit): a plausible cause was reached
before the owner had finished saying what happened, and it fitted the shape of
the anomaly well enough to be believed.

**A 50% boost would not have explained a zero move anyway** — it turns the
predicted `3.42%` into roughly `2.3%`, not `0`. Only a reset does.

**The boost still matters, forward.** It ends **September 13**, and a reading
taken after that is against a denominator 50% smaller than every reading above
it. So the rule survives its own wrong reasoning: **record the boost state, and
record any reset you are told about, beside any gauge reading meant to be
kept.** Neither is visible in the output, and without them a percentage cannot
be compared with another percentage.

**So the DERIVATION is retired rather than re-fitted.** Fitting a fifth anchor
to a fifth reading is how the last four got their false precision.

### The percentage itself stays, because it is what the owner plans with

**Corrected again, after asking him how he actually estimates** — which no
session in this cycle had done, while four of them argued about his numbers. In
his words: he *"hasn't really been paying much attention to the dollar amounts
themselves"* and watches the usage percentage, *"as that's the only thing that
seems to remain roughly the same with the numbers — within reason; different
models and different tasks affect this for sure."*

**His method:** keep a running tally of **how many percent a big cycle costs**,
predict the next from it, and **update the model when a run breaks the
pattern.** That is P-41 exactly — an estimate from a stated model, corrected by
measurement — and it divides nothing by anything.

**An earlier version of this finding retired the percentage column outright, and
that was an over-correction.** What has been wrong every single time is
*deriving* a percentage; *reading* one has never been wrong, and it is the only
number that governs when he actually has to pause. Removing it would have taken
away the one instrument in this table that its reader uses, in the name of
accuracy.

**The distinction is the whole finding, and it is worth stating flatly:**

| | Verdict |
|---|---|
| **read** the gauge, before and after, and record it | **do this** — it is the owner's planning instrument |
| record the **boost state** and any **reset** beside it | **do this** — without them, no two readings are comparable |
| **dollars and requests**, read | **do this** — not his bill, but an exact size measure *between* sessions |
| **derive** a percentage from dollars, tokens, or a chained anchor | **never** — wrong every time, and this subcycle's would have been wrong by three points |

**The general shape, which is the part worth carrying:** four sessions
disagreed about how to compute a number for a reader nobody had asked how he
reads it. The answer took one question. **An instrument is calibrated against
the decision it feeds, not against its own internal consistency** — and the
decision here was always "when does he pause", which only the gauge answers.

**The one thing worth watching**, for whoever gets a reading that does move:
this session was 98.8% cache reads across `66.4 M` cache-read tokens, which is
expensive in dollars and may be cheap in whatever the gauge actually meters. If
a future subcycle with a different cache profile moves the display, that is the
measurement that would settle it. Nobody should build a model on it before then.

**And the ask itself is the standing instruction that worked.** §8 says to ask
the owner for the dollar figure before writing any percentage. Doing that is
what produced this finding: a session deriving its own number from tokens would
have written `3.42%` into the table, and the fifth reader in a row would have
inherited it.
