### 3.2 Overlay in a user namespace (spec S-2)

A script, not typed by hand, so it can be re-run: create `lower/` with
`tracked.txt` = `v1` and `gone.txt`; `upper/`, `work/`, `merged/` empty; then

```bash
unshare --user --map-root-user --mount sh -c '
  mount -t overlay overlay -o lowerdir=lower,upperdir=upper,workdir=work merged &&
  printf v2 > merged/tracked.txt && printf new > merged/added.txt && rm merged/gone.txt &&
  ls -la upper'
```

Expected: exit 0; host `lower/tracked.txt` still `v1` and `lower/gone.txt`
still present (byte-identical: `sha256sum` before and after); `upper/`
holds `tracked.txt` (`v2`), `added.txt`, and `gone.txt` as a character device
`c--------- … 0, 0` — the whiteout, spec §6.1. **Never walk `upper/` to
compute a diff**; this probe exists so you have seen why.

`Observed.` **2026-09-07, `MEASURED`. Exactly as expected.** Exit `0`. The
lower layer is byte-identical after the run — `sha256sum` before and after
gave `3bfc2695…` for `tracked.txt` and `75b184f4…` for `gone.txt`, and
`gone.txt` is still there. `upper/` holds:

```
-rw-rw-r-- 1 randy randy    3 added.txt
c--------- 2 randy randy 0, 0 gone.txt      <- the whiteout
-rw-rw-r-- 1 randy randy    2 tracked.txt
```

`/proc/self/uid_map` inside the `unshare` is `0 1000 1`.

This row is now also `sandbox_probe.py`'s last row, run on every `setup`, and
the check it makes is the one worth naming: **it re-reads the lower layer and
requires it byte-identical**, because an overlay that silently wrote through
would pass "did the mount command exit 0?" while destroying the repository it
was mounted to protect. The control plants exactly that
(`overlay-wrote-through-to-the-lower-layer`).

### 3.3 The headless worker inside the composition (spec S-6, brought forward)

The probe that matters. Compose spec §5 by hand for one throwaway git
repository (`git init`, one commit), and run a real headless `claude -p`
inside it with a one-line task. Bind the merged view **at the same absolute
path as the throwaway repo on the host** (L-3). Bind the plugin directory
read-only at its host path. `HOME` is a tmpfs.

Three variants, run in this order, each with the cases below:

| Variant | Credentials | Expected |
|---|---|---|
| A | `~/.claude/.credentials.json` copied into the tmpfs `HOME/.claude/` (a *copy*, so a token refresh inside cannot touch the host's file) | the CLI authenticates and runs |
| B | an environment variable carrying an OAuth or API token, name taken from the CLI's own documentation (`claude --help`, the docs) — `REASONED`: the variable's name is not known to this plan | same |
| C | nothing | **must fail** to authenticate — this is the known-deny case (L-0.2) |

Run inside, with `--output-format json --plugin-dir <plugin> --model <cheapest>`
and a prompt of the form *"Invoke the devteam:work skill's inputs section,
then create the file `<repo>/hello.txt` containing `hello` using the Write
tool, then run `cat /proc/self/uid_map` with Bash and report both outputs."*

Record, for the variant that works:

1. `hello.txt` appears in `upper/`, **not** on the host (`ls` both).
2. the JSON result's `result` field carries the two outputs; the `uid_map`
   line is not the host's identity map (the Bash tool ran inside).
3. the JSON's usage / cost fields — note their exact names; 0.2.3 reads them.
4. what the CLI wrote under the tmpfs `HOME` (`ls -R "$HOME/.claude"` as a
   trailing command in the same `bwrap` invocation): session files, caches,
   a rewritten credentials file. This is the list of things a worker's
   `HOME` must be allowed to hold.
5. wall-clock and whether the `work` skill was actually loaded (the result
   should quote its inputs section; if it does not, `--plugin-dir` did not
   take effect headless — record that, it changes 0.2.3).
6. whether the CLI attempted to sandbox its own Bash (the harness's built-in
   sandbox, `../README.md` §4.2): pass `--settings '{"sandbox":{"enabled":false}}'`
   on one run and omit it on another, and compare the `uid_map` output and
   any `[Sandbox Linux]` lines. Nested `bwrap` under our `bwrap` is the case
   to know about, not to prevent.

`Observed.` **2026-09-07, `MEASURED`. Variant A works. L-2 stands and the
cycle proceeds as written.** Four runs on `claude-haiku-4-5-20251001`,
`$0.062` in total.

**The composition that worked**, which is 0.2.1's input rather than a
description of it. `$P` is scratch, `$HOSTREPO` the repository's own absolute
path (L-3), `$PLUGIN` the plugin at its host path:

```bash
unshare --user --map-root-user --mount sh -c "
  mount -t overlay overlay \
    -o lowerdir=$HOSTREPO,upperdir=$P/upper,workdir=$P/work $P/merged || exit 9
  bwrap --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp \
    --bind $P/home /home/<user> \
    --ro-bind /home/<user>/.local /home/<user>/.local \
    --ro-bind $PLUGIN $PLUGIN \
    --bind $P/merged $HOSTREPO \
    --clearenv \
    --setenv HOME /home/<user> --setenv USER <user> --setenv LANG C.UTF-8 \
    --setenv PATH /home/<user>/.local/bin:/usr/local/bin:/usr/bin:/bin \
    --setenv TERM dumb \
    --unshare-user --uid 1000 --gid 1000 \
    --unshare-pid --new-session --die-with-parent --chdir $HOSTREPO \
    -- /home/<user>/inside.sh"
```

Four things in it are not decoration, and each was learned by its absence:

- **`--unshare-user --uid 1000 --gid 1000`.** Without it the worker is uid 0,
  because `--map-root-user` made it so, and the CLI refuses:
  `--dangerously-skip-permissions cannot be used with root/sudo privileges for
  security reasons`. The outer stage has to be root in its namespace to mount
  the overlay; the inner stage has to not be, to run a worker. bwrap's nested
  namespace is where the two are reconciled.
- **`-- /home/<user>/inside.sh`, a file, not a quoted command string.** See
  the first finding below.
- **`--bind $P/home /home/<user>` before the two `--ro-bind`s under it.**
  bwrap applies mounts in order, so the ro-binds re-create their paths inside
  the replacement home; reversed, they are shadowed by it.
- **`--ro-bind / /` needs its mount points to exist.** `--tmpfs /home/probe`
  fails with `Can't mkdir /home/probe: Read-only file system`. Every tmpfs and
  bind target must be a path that already exists on the host, or be created
  under one that does.

**Order of the mounts matters more than the list of them**, and that is worth
carrying into `sandbox.py`'s mount plan as an ordered list rather than a set.

**Variant A — a copy of `~/.claude/.credentials.json` in the sandbox HOME:

### 3.4 Background lifetime (`../README.md` §4.5)

From a session with the `Bash` tool: run the 3.3 composition with a command
of `sleep 720; echo survived` using `run_in_background`, and separately with
`--die-with-parent` removed. Expected, `REASONED`: the backgrounded process
survives the ten-minute foreground limit and the session is re-invoked when
it exits with `survived` in its output. If the `--die-with-parent` variant
survives and the other does not, the background shell is not a stable
parent, and 0.2.3 §3.4 changes to a detached process with its own reaper.

`Observed.` **2026-09-07, `MEASURED`. It survives — and the probe found that
the question has two halves, only one of which this section asked.**

Both variants ran `sleep 720` and both came back: `A exit=0` and `B exit=0` at
`02:08:36`, 720 seconds after `01:56:36`, each having written its marker into
its own `upper/` with the host's lower layer untouched. Ten minutes is not a
ceiling on a backgrounded sandbox, and `--die-with-parent` did not shorten it.

**But `--die-with-parent` binds the sandbox to whatever process is actually
its parent, and that is the thing to get right rather than the survival
time.** In this run the parent was a detached script that stayed alive for the
duration, so the flag had nothing to kill. That is the arrangement 0.2.3 wants
anyway — the supervisor backgrounds a launcher, the launcher holds the
sandbox, and killing the launcher reaps the sandbox — but it is a *different*
arrangement from backgrounding the `bwrap` invocation itself, where the parent
is a shell the harness owns and whose lifetime is not documented. That second
case is measured separately below because 0.2.3 §3.4's branch depends on which
one is true, and answering it with the first would have been the same mistake
as §3.3's plugin reading: an instrument answering a question adjacent to the
one asked.

`Observed (the harness's background shell as the direct parent).` **2026-09-07,
`MEASURED`. It survives that too.** The `bwrap` invocation backgrounded
directly by the tool — no launcher script between them — ran `sleep 660` and
returned `survived-direct`, `exit=0 at 02:20:19`, 660 seconds after
`02:09:19`. Its marker is in `upper/`; the host's lower layer is empty.

**So the harness's background shell is a stable parent, and
`--die-with-parent` is the whole reaper.** 0.2.3 §3.4 needs no detached
process, no pidfile and no reaper of its own; a supervisor backgrounds
`sandbox.py run` and killing that call reaps the worker and its build
processes together, which is what §6.3 of the spec asks for.

**What it would have changed:** if this case had failed while the first
passed, 0.2.3 §3.4 would take the plan's detached-process-with-a-pidfile
branch, and the launcher used in the first run is what that branch looks
like. Neither is needed. Recorded because the two runs look identical in
their output and are not the same measurement — the first one's parent was a
script that outlived the sandbox by design.

### 3.5 `SendMessage` to a session whose turn has ended

Needed by 0.2.5 (rotation). From a second session on this machine, send a
message to this one after this one has ended its turn. Expected, `REASONED`:
`ListAgents` lists it as a local session and the message wakes it. If it
does not, rotation's live exchange (`resume` §0) only works while the outgoing
session is mid-turn, and 0.2.5 §3.2 must say so.

`Observed.` **2026-09-07. Half measured, half deliberately not run.**

`ListAgents` from this session listed eight peer interactive sessions on this
machine by name — including two other `claude-skills` sessions idle for a day
— each addressable as `SendMessage({to: "<name>"})`. So the addressing half
holds: **a session that has ended its turn is still listed and still has an
address.** `MEASURED`.

The waking half was **not** run, and the reason is a constraint rather than an
oversight. Every peer on this machine is one of the owner's live working
sessions in a sibling repository, and a probe message writes into that
session's context — work this session cannot see and did not ask to disturb.
That is the same rule as "do not write outside this repository", one level up:
a session's context is state somebody else is holding.

**What 0.2.5 must do before it depends on this**: ask the owner to run the
probe with two sessions he has opened for it, or have rotation's outgoing
manager send the first message rather than the incoming one — which needs no
wake at all, because the outgoing session is by definition mid-turn when it
hands over. **The second is the better design and 0.2.5 should prefer it**:
it removes the dependency instead of measuring it, and rotation then works
whether or not an ended turn can be woken.

## 4. The decision rule

Write the outcome under `## Findings` at the foot of this file, then:

- **3.1 exits 0, 3.2 as expected, 3.3 works in variant A or B, 3.4 survives**
  → proceed to 0.2.1 as written.
- **3.3 fails for a reason one session can fix** (a missing bind, an
  environment variable) → fix, re-run, record, proceed.
- **3.3 fails structurally** (the CLI cannot authenticate from a cleared
  environment at all; the plugin cannot load headless) → switch the cycle to
  the fallback branch below and supersede L-2 in `../README.md` §6 with the
  reason measured.
- **3.4 fails** → 0.2.3 §3.4 uses a detached process with a pidfile and its
  own reaper; nothing else changes.

### The decision, 2026-09-07

**The first branch. 3.1 exits 0, 3.2 was exactly as expected, 3.3 works in
variant A, and 3.4 survives. Proceed to [0.2.1](../0.2/0.2.1.md) as written.** L-1
through L-4 all stand; none is superseded. §6's fallback branch stays
specified and unbuilt.

Three things 0.2.1 must carry that were not in its inputs when it was planned,
each from a finding below:

1. **The mount plan is an ordered list, not a set.** bwrap applies mounts in
   sequence and a bind under a replacement `HOME` is shadowed if it is
   declared first. `sandbox.py`'s mount plan should be a list whose order is
   part of its contract, with a comment saying why.
2. **`run` and `exec` write the inner command to a file and execute the
   file.** Never interpolate a command into a quoted string; three levels of
   quoting is what produced this subcycle's one false reading.
3. **`open` seeds `user.name` and `user.email`** into the overlay's
   repository config, or the worker's first commit fails with
   `Author identity unknown` for a reason unrelated to its task.

And one that belongs to 0.2.3 rather than 0.2.1, recorded here so it is not
rediscovered: the dispatch reads **`is_error`**, never `subtype`, and passes
**`--strict-mcp-config`** and **`--unshare-user --uid <uid> --gid <gid>`**.

  about, the one that changes 0.2.3. It was wrong. The same flag with the same
  path on the host loaded all fifteen `devteam:*` skills; moving the inner
  command out of a `bash -lc '…'` inside a `sh -c "…"` and into a script file
  inside the sandbox made it load inside too. The fault was three levels of
  quoting, not the sandbox. **What it changes:** `sandbox.py`'s `run` and
  `exec` must write the inner command to a file and execute the file — never
  interpolate a command into a quoted string. And this is P-35b arriving on
  schedule: an instrument built in a hurry answered a question it was not
  wired to ask. L-0.1 is what caught it, because writing the observed output
  down beside the expected output is what makes a wrong instrument look like a
  claim rather than a fact.

- **`--permission-mode bypassPermissions` is refused when the process is
  root.** `--dangerously-skip-permissions cannot be used with root/sudo
  privileges for security reasons`, and `--map-root-user` is what made it
  root. **What it changes:** the inner stage carries
  `--unshare-user --uid 1000 --gid 1000`. The outer stage must be namespace
  root to mount the overlay and the inner stage must not be to run a worker;
  bwrap's nested namespace is where those two requirements are reconciled.
  0.2.3 should not read the uid from the host — it should pass the invoking
  user's real uid and gid explicitly.

- **A failed run reports `subtype: "success"`.** Variant C came back with
  `is_error: true`, `terminal_reason: "api_error"`,
  `result: "Not logged in · Please run /login"` — and `subtype: "success"` in
  the same object. **What it changes:** 0.2.3's dispatch branches on
  `is_error`, never on `subtype`, and its control plants a failed run whose
  `subtype` says otherwise. A supervisor that read `subtype` would accept an
  unauthenticated worker's empty output as a completed step.

- **`git` inside the sandbox has no author identity, and refuses to commit.**
  `Author identity unknown` — measured with an otherwise working composition.
  `--clearenv` and a replacement `HOME` remove `~/.gitconfig` along with
  everything else. **What it changes:** `sandbox.py open` seeds
  `user.name` and `user.email` in the overlay's repository config, from the
  host's values, or the worker's first commit fails for a reason that has
  nothing to do with its task.

- **L-4's "`git push` has nothing to authenticate with" is now `MEASURED`
  rather than reasoned** — and it is a consequence of the same fact. The
  replacement `HOME` contains no `~/.ssh`, no `~/.gitconfig` and no `gh`

  impossible inside, as L-4 argued it would be.

- **The containment is wider than L-3 claimed: sibling repositories are not
  merely read-only inside, they are absent.** A write to
  `~/Workspace/REPOS/claude-skills/README.md`, spelled absolutely, from inside
  the sandbox failed with `No such file or directory`, because the replacement
  `HOME` shadows everything under it and only the bound paths are re-created.
  **What it changes:** nothing that has to be built — but it means the owner's
  standing rule against writing into a sibling repository, which the guard
  enforces by parsing paths, is enforced by the mount table for anything
  running inside. Say so in 0.2.4 where that rule is documented, so a reader
  knows which mechanism is holding it.

- **`git commit --amend` inside rewrote only the overlay's history.** After an
  amend inside, the host's `HEAD` was unchanged and the amended commit existed
  only in the merged view. **What it changes:** nothing — it confirms it.
  This is `../README.md` §2's expensive class (F-71, F-73, F-81, and the
  worker half of F-135) measured as structurally contained, which is the claim
  the whole architecture was chosen for. It was `REASONED` when the cycle was

- **A sandboxed worker connected to the owner's Google Drive, successfully,
  in 11 milliseconds, from inside a container built to stop it writing to the
  filesystem.** Not "attempted" — the connector log reads
  `Successfully connected (transport: claudeai-proxy) in 11ms` and
  `Connection established with capabilities: {"hasTools":true,…}`, over
  `https://mcp-proxy.anthropic.com/v1/mcp/<server id>`. The sandbox's `HOME`
  had no MCP configuration at all, the host has no `/etc/claude-code/` and no
  `mcpServers` in `~/.claude.json`, and nothing was passed in but the copied
  credentials. **The connectors are attached to the account and travel with
  the token**, through the same authenticated channel as the model itself, so
  clearing the environment and replacing the home does not clear them.
  **What it changes:** L-4 accepted "a worker can reach the network" on the
  grounds that the threat model is filesystem writes — but a first-party
  document connector is a write, to somewhere outside the machine entirely,
  and no overlay touches it. This is not a hole in the sandbox; it is a hole
  in the sentence L-4 used to bound the sandbox's job. On this machine the
  drive behind that connector holds several hundred research documents from
  the planning of two other projects, which is the concrete shape of what an
  unflagged worker could read or change: not a hypothetical corpus.
  **The mitigation is `MEASURED`, not assumed.** Two otherwise identical
  sandboxed runs, differing only in the flag: without `--strict-mcp-config`,
  `.cache/claude-cli-nodejs/<slug>/mcp-logs-claude-ai-Google-Drive/` is
  created; with it, no `mcp-logs-*` directory appears at all, and the run
  succeeds either way. 0.2.3 passes it, and 0.2.4 records it as the second
  reason the flag is not optional. Worth one more sentence, because it is the
  part a reader will get wrong: this closes the connectors the *CLI* would
  start, and it is not a network control. L-4's trigger for unsharing the

- **This subcycle's composition is not the one 0.2.1 specifies, and the

  so neither is rediscovered:

      of `--ro-bind / /`, **not** of 0.2.1's plan. Under a tmpfs root bwrap
      creates its own mount points, so §3.2's `/home/devteam-worker` — a path
      that deliberately exists nowhere on the host — works exactly as written.
      The probe's `Can't mkdir /home/probe: Read-only file system` will not
      recur there.
    - ~~the finding above about sibling repositories being absent holds under
      0.2.1's plan **more** strongly and for a simpler reason: they are never
      bound, rather than bound and then covered.~~
      **WRONG. Struck 2026-09-07 by 0.2.1, which measured it.** The opposite

- **`~/.local/bin/claude` is a symlink into a versioned directory, so binding
